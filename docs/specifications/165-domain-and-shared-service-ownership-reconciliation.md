# 165 — تسوية حدود ملكية المجال والخدمات المشتركة وسجل فجوات SH-17–SH-20

**التاريخ:** 2026-11-16  
**الحالة:** DERIVED OWNERSHIP RECONCILIATION / OWNER REVIEW REQUIRED / NOT APPROVED / NOT IMPLEMENTED.  
**المراجع الأساسية:** 72 و81 و83–91 و157 و164.

## 1. الغرض

توحيد قواعد الفصل بين Domain System of Record (Domain SoR) وShared Service System of Record (Shared Service SoR)، وإظهار مواضع التداخل التي تمنع اعتماد العقود والبيانات والاختبارات. هذه الوثيقة لا تعيّن مالكاً فعلياً ولا تعتمد قرارات OWN؛ إنها تسوية تحريرية بين workpapers قائمة.

## 2. القواعد الحاكمة

1. لكل حقيقة مجالية canonical owner واحد، ولا تنشأ نسخة قابلة للكتابة لدى المستهلك لمجرد الحاجة إلى العرض أو الفهرسة أو التشغيل.
2. الخدمة المشتركة تملك metadata التشغيلية والوظيفة الأفقية المحددة لها، ولا تملك معنى مورد المجال أو lifecycle الخاص به.
3. SH-03 ينفذ workflow الموافقات مركزياً ضمن النطاق المصدري C01–C14؛ لا يصبح بذلك Decision Owner ولا يقرر نيابة عن مالك المجال.
4. C14 يملك تخطيط العرض وتفضيلات اللوحة، لا حقائق المقاييس التي يعرضها.
5. وجود اسم خدمة أو مرجع OWN أو API operation في سجل مشتق لا يساوي اعتماد Domain SoR أو Qualified OWN أو API Owner.
6. كل كتابة حساسة يجب أن تمر عبر مالك حقيقة المجال، وتتحقق من scope والصلاحيات والنسخة/البصمة والموافقة المطلوبة وفق السياسة.
7. لا تدمج سجلات الملكية المتصادمة ولا تعِد ترقيمها بصمت؛ يجب أن يذكر كل مرجع رقم الوثيقة/السجل الذي ينتمي إليه.

## 5. تفاصيل تحتاج قرارات مالكين منفصلة

### 5.1 المؤسسة ومساحة العمل والأدوار
الوثيقة 84 تبقي مالك حقيقة المؤسسة ومساحة العمل والعضويات والتعريف الدلالي للأدوار مفتوحاً. لا يثبت SH-01/SH-02 الملكية لمجرد أنهما يقدمان الهوية والتفويض. كما أن organization_id وtenant_id ليسا مترادفين تلقائياً، وworkspace_id مرجع نطاق لا يمنح صلاحية.

### 5.2 الإصدارات ومجموعات التغيير
الوثيقة 85 تفصل canonical domain content عن version metadata في SH-10، وتفصل كذلك record_version/expected_version عن version_id/parent_version وcontractVersion وartifactVersion وreleaseVersion وchangeSetId. مالك artifact registry، وbranch/merge/restore semantics، وحدود C11 ما زالت تحتاج قراراً.

### 5.3 الإعدادات والأسرار
الوثيقة 86 تبقي precedence وترتيب الوراثة والنطاقات والـoverride authority مفتوحة. SH-12 يخزن القيم غير السرية ومراجع الأسرار وفق ما يعتمد؛ لا تُخزن القيمة السرية الفعلية في سجلات الإعدادات أو السجلات والأحداث.

### 5.4 المعرفة والفهرسة
الوثيقة 90 تقترح أن C12/مالك المجال يملك المحتوى والنسخ والاعتماد، بينما SH-16 يملك metadata ingestion/index/provenance وSH-07 يملك search runtime. يجب إعادة التحقق من ACL عند الاسترجاع، ولا يصبح embedding أو snippet أو answer حقيقة أصلية.

### 5.5 الموصلات والتكاملات
الوثيقة 91 تقترح أن C09 يملك غرض التكامل والخرائط وسياسات المزامنة، وSH-13 يملك runtime metadata ودورة حياة الاتصال، بينما Secret Manager يملك القيمة السرية. جميع قرارات الحزمة OPEN، ولا توجد قائمة مزودين أو نطاقات OAuth معتمدة بهذه الوثيقة.

## 6. SH-03: نطاق الخدمة مقابل التكامل الفعلي

وفق التسوية المصدرية في الوثيقة 157، الفصل 126.1 يثبت أن خدمة الموافقات المركزية تخدم جميع المراكز C01–C14. لذلك فإن مصفوفة التسعة مراكز القديمة لا تمثل النطاق الكامل.

لكن يجب التمييز بين:
- **Service scope:** جميع المراكز ضمن النطاق المركزي — مثبت مصدرّياً.
- **Direct integration:** هل يستهلك المركز endpoint أو workflow محدداً — لم يُحسم لكل مركز.
- **Approval requirement:** هل يتطلب الفعل موافقة إلزامية/مشروطة/لا يحتاج موافقة — يحدده مالك المجال والسياسة.
- **Decision ownership:** يبقى لدى صاحب قرار المجال، لا SH-03.

كما أن دورة Request → Decision → Execution → Verification → Reversal/Revocation يجب أن تبقى مراحل منفصلة. requestQualityWaiver لا يساوي approveQualityWaiver، ووجود عمليات deploy/publish/apply لا يثبت قرار الموافقة.

## 7. فجوة SH-17–SH-20

تُظهر الفهارس وحزم العمل التي تمت مراجعتها عقوداً وقرارات للخدمات المشتركة حتى SH-16. لم يُعثر في الأدلة المراجعة هنا على تعريف مصدر موثوق لـSH-17 أو SH-18 أو SH-19 أو SH-20، ولا على اسم أو مسؤولية أو مالك أو عقد يمكن نسبته إليها.

| الخدمة | تعريف مصدر مستعاد | مالك/SoR | عقد/اختبارات | الحالة |
|---|---|---|---|---|
| SH-17 | لا يوجد في الأدلة التي تمت مراجعتها | TBD | TBD | SOURCE GAP |
| SH-18 | لا يوجد في الأدلة التي تمت مراجعتها | TBD | TBD | SOURCE GAP |
| SH-19 | لا يوجد في الأدلة التي تمت مراجعتها | TBD | TBD | SOURCE GAP |
| SH-20 | لا يوجد في الأدلة التي تمت مراجعتها | TBD | TBD | SOURCE GAP |

هذا لا يثبت عدم وجودها في كل الأرشيف أو المحادثات؛ يثبت فقط أن تعريفها لم يستعد في مجموعة المصادر التي تمت مراجعتها لهذه الوثيقة. لا يجوز اختراع أسماء أو وظائف لها أو تمديد SH-01..SH-16 تلقائياً.

## 8. بوابة اعتماد موحدة لكل حد ملكية

لا يغلق أي OWN أو حد خدمة حتى يسجل:
1. المصدر الدقيق ورقم الفصل/الفقرة، مع تمييز النص الحرفي عن الاستنتاج.
2. الكيان/الحقل/العملية/الحدث المعني، وcanonical Domain SoR.
3. Shared Service SoR وسبب امتلاكها للـmetadata أو التشغيل فقط.
4. Qualified Owner بالاسم الوظيفي/الجهة المخولة، وقرار الموافقة وتاريخه.
5. producer/consumer والواجهات المسموحة واتجاه الكتابة.
6. tenant/workspace/project/environment scope وACL وclassification.
7. versioning/concurrency/idempotency/audit semantics.
8. اختبارات contract وnegative authorization وcross-tenant، وروابط exact معتمدة.
9. أثر القرار على المراكز الأخرى والعقود والحقول والأحداث والموافقات.
10. حالة القرار: PROPOSED أو OWNER REVIEW أو APPROVED، مع دليل الموافقة.

## 10. الحكم

تؤكد هذه المراجعة أن نموذج Domain SoR مقابل Shared Service SoR قابل للتعبير بصورة متسقة، لكن الاعتماد الفعلي غير مكتمل. أكبر مخاطر الإغلاق الحالية هي تصادم معرفات OWN بين الوثيقتين 36 و72، وعدم حسم ملاك المؤسسة/مساحة العمل وبعض الخدمات، وغياب تعريف SH-17–SH-20 في المصادر المراجعة، وعدم وجود دليل اعتماد نهائي لقرارات OWN.

**لا تنشئ هذه الوثيقة APIs أو جداول أو خدمات أو صلاحيات. لم يتغير كود التطبيق أو قاعدة البيانات. لا تمنح إذناً بالبرمجة؛ يظل ذلك متوقفاً حتى اكتمال المواصفات وموافقة المستخدم الصريحة المستقلة على بدء التنفيذ.**
