# 03 — المعمارية والبيانات والأمن

## 1. المبادئ المعمارية

1. فصل واجهة المصمم عن محركات التنفيذ والتصميم والبرمجة.
2. البدء بمعمارية Modular Monolith عندما يكون ذلك مناسباً، وعدم تفكيك النظام إلى خدمات صغيرة بلا حاجة مثبتة.
3. ملكية نطاقية واضحة للبيانات والخدمات.
4. مصدر حقيقة واحد لكل كيان وقرار.
5. عقود API وأحداث موثقة وإصدارات متوافقة.
6. استخدام محولات لربط التقنيات ومزودي AI والمنصات.
7. دعم المهام الطويلة بنقاط تحقق واستئناف ومنع تكرار.
8. فصل بيانات المصمم عن بيانات التطبيقات التي ينشئها.
9. عدم السماح للمكونات أو الوكلاء بتجاوز بوابات الأمن والموافقة.

## 2. طبقات المنتج المستهدف

### الطبقة الأولى — واجهة المصمم
- Angular هو الاختيار المعتمد كالتقنية الأساسية لواجهة المصمم.
- واجهات عربية وRTL مع قابلية التعدد اللغوي.
- مساحة عمل للمشاريع والمراكز الأربعة عشر.
- معاينات مستقلة للمنصات المستهدفة.
- لا تحتوي الواجهة على أسرار أو صلاحيات خادمية حساسة.

### الطبقة الثانية — خدمات التطبيق والتنسيق
- إدارة المشاريع والمتطلبات والموافقات.
- إدارة الهوية والصلاحيات.
- تنسيق المهام والوكلاء.
- إدارة الإصدارات والتغييرات.
- الإشعارات وسجل التدقيق.
- السياسات والميزانيات والمراقبة.

### الطبقة الثالثة — المحركات المستقلة
- محرك التصميم.
- محرك البرمجة.
- محرك البيانات والمخططات.
- محرك التنقل والصفحات.
- محرك الاختبارات والجودة.
- محرك فهم المستندات والصور والتصاميم.
- محرك البناء والنشر.
- محرك المعرفة والتوثيق.

### الطبقة الرابعة — المحولات والإضافات
- محولات أطر الواجهة والتقنيات.
- محولات لغات البرمجة.
- محولات قواعد البيانات والتخزين.
- محولات مزودي الذكاء الاصطناعي.
- محولات أنظمة البناء والنشر.
- إضافات ذات صلاحيات محددة وعقود واختبارات توافق.

### الطبقة الخامسة — بيئات التنفيذ
- Sandbox لتوليد الكود وتشغيله واختباره.
- بيئات تطوير واختبار وتجهيز وإنتاج منفصلة.
- Workers للمهام طويلة المدى.
- تخزين ملفات وأصول.
- خدمات مراقبة ونسخ احتياطي واستعادة.

## 3. قرارات تقنية معروفة

| المجال | القرار أو الاتجاه | الحالة |
|---|---|---|
| واجهة المصمم | Angular | معتمد |
| محرك التصميم | مستقل عن Angular | معتمد |
| محرر الكود | Monaco | اختيار معتمد للمحرر |
| محرك البرمجة | مستقل عن إطار الواجهة | معتمد |
| توليد الكود | نموذج وسيط IR ثم محولات | اتجاه معماري معتمد |
| تدفقات العمل | محرك مخططات/تدفقات قابل للتبديل | معتمد |
| المعمارية | Modular Monolith أولاً مع حدود نطاقية | اتجاه معماري |
| الاعتماديات | نمط هجين: تلقائي ضمن السياسات، موافقة للقرارات عالية الأثر | معتمد |
| المنصات | متعددة المنصات وقابلة للتوسع | نطاق معتمد |

هذه القرارات تخص المنتج المستهدف، ولا تعني أن التطبيق Android الحالي قد تم تحويله أو أن كل المحولات قد اختيرت.

## 4. نموذج العمل مع الذكاء الاصطناعي

- Orchestrator ينسق المهام ولا يمتلك الصلاحيات المطلقة.
- الوكيل له دور ومهارات وأدوات مسموح بها وحدود تكلفة وبيانات.
- ذاكرة كل مشروع معزولة عن المشاريع الأخرى.
- الاقتراح منفصل عن التنفيذ.
- كل مهمة طويلة تحفظ حالتها ونقاط تحققها ومخرجاتها.
- دعم الإيقاف والاستئناف وإعادة المحاولة.
- استخدام idempotency للعمليات الخارجية الحساسة.
- التحقق من الموافقة قبل الخطوات عالية الأثر.
- تسجيل المزود والنموذج والتكلفة والرموز والمدة والأخطاء.
- لا تُرسل بيانات أو ملفات إلى مزود AI إلا وفق سياسة المشروع والموافقة اللازمة.

## 5. البيانات وملكية النطاق

يجب تعريف نطاقات البيانات والملكية، ومنها:
- المؤسسة والمستخدمون والعضويات.
- المشاريع والمتطلبات والافتراضات والأسئلة والتعارضات.
- التصميم والصفحات والعناصر والمكونات والرموز.
- التنقل والمسارات والروابط.
- قواعد البيانات والمخططات والاستعلامات والربط.
- الكود والملفات والتغييرات والإصدارات.
- الوكلاء والمهارات والمهام ونقاط التحقق.
- الاختبارات والعيوب وتقارير الجودة.
- التكاملات والموصلات والأسرار.
- الموافقات وسجلات التدقيق.
- البناء والحزم والنشر والمراقبة.
- المعرفة والوثائق والقرارات.
- النسخ الاحتياطي والتعافي.

الحقول المشتركة المتوقعة تشمل معرفاً ثابتاً، ومالك النطاق، ومعرف المؤسسة/المشروع عند الحاجة، وإصدار السجل، وحالة دورة الحياة، وحقول الإنشاء والتحديث، ومصدر المعلومة، ومنفذ التغيير.

## 6. قواعد البيانات والتزامن

- فصل قواعد بيانات المصمم عن قواعد التطبيقات المنشأة.
- فصل التطوير والاختبار والإنتاج.
- تعريف migrations وإصدارات المخططات.
- عدم افتراض أن التراجع عن migration يعيد البيانات المحذوفة.
- استخدام Outbox عند الحاجة لضمان نشر الأحداث.
- استخدام Saga للعمليات متعددة الخطوات عند الحاجة.
- idempotency لمنع تكرار الأثر الخارجي.
- قيود وفهارس وعلاقات واضحة.
- اختبار النسخ الاحتياطي والاستعادة على بيئة منفصلة.
- لا يُسمح بتغيير إنتاجي دون موافقة معتمدة.

## 7. الأمن والخصوصية

### الهوية والعزل
- أقل صلاحية افتراضياً.
- عزل المؤسسة والمشروع على مستوى الخادم والبيانات.
- التحقق من هوية المستخدم والعضوية والصلاحية عند كل عملية حساسة.
- إدارة الجلسات والأجهزة وانتهاء الصلاحيات.

### الأسرار
- تخزين الأسرار في خزنة آمنة أو خدمة أسرار مناسبة.
- عدم تخزين القيم السرية كنص صريح في مستندات المشروع أو سجلاته.
- عرض قيمة مقنّعة فقط للمستخدم عند الحاجة.
- تحديد الخدمات والوكلاء والعمليات المسموح لها باستخدام كل سر.
- دعم انتهاء الصلاحية والتدوير والإبطال.

### الوكلاء والإضافات
- لا يمنح الوكيل نفسه صلاحيات.
- لا يقرأ الوكيل إلا البيانات الضرورية لمهمته.
- لا تنفذ الإضافة أو المحولة إلا ضمن صلاحيات معلنة ومراجعة.
- عزل Sandbox ومنع الوصول غير الضروري للشبكة والملفات والأسرار.
- مراجعة المدخلات غير الموثوقة وعدم اعتبارها تعليمات موثوقة.

### التدقيق
- تسجيل الفاعل والعملية والوقت والهدف والسبب والنتيجة ومعرف الموافقة.
- حماية سجلات التدقيق من التعديل بواسطة الوكلاء.
- ربط التغيير بالطلب والإصدار والاختبار.
- لا تُغلق ثغرة دون إعادة اختبار.

## 8. فهم الصور والمستندات والتصاميم

يجب أن يدعم المركز:
- تحليل صور واجهات التطبيقات واستخراج العناصر.
- تحليل PDF وWord وExcel وPowerPoint.
- تحليل المخططات والرسومات ولقطات الشاشة.
- تحليل الفيديوهات التوضيحية عند توفر مسار معالجة معتمد.
- استخراج النصوص والجداول والبيانات.
- مقارنة نسختين من التصميم واكتشاف الاختلافات.
- تحويل الرسومات اليدوية إلى عناصر أولية قابلة للتحرير.
- إظهار مصدر كل نتيجة ومستوى الثقة والمواضع غير المؤكدة.
- طلب مراجعة بشرية عند انخفاض الثقة أو ارتفاع أثر الخطأ.

## 9. الاعتمادية واستمرارية المصمم

- مراقبة صحة الخدمات والعمال والاتصالات.
- كشف الأعطال مبكراً.
- تفعيل بديل للخدمة وفق سياسة محددة.
- نسخ احتياطية لإعدادات المصمم وبياناته الأساسية.
- استعادة الجلسات والمهام من نقاط تحقق.
- حماية المهام من التنفيذ المكرر.
- اختبار خطط التعافي دورياً وتوثيق نتائجها.
- قياس RTO وRPO بعد اعتماد الأهداف المناسبة.

## 10. الأداء والتكاليف

- قياس P50/P90/P95/P99.
- قياس زمن الاستجابة والذاكرة والمعالج والتخزين.
- قياس استهلاك AI tokens وتكلفة كل مهمة ومشروع.
- حدود شهرية وتنبيهات وموافقات عند تجاوز الحدود.
- خيارات بديلة عند تعطل مزود أو تجاوز حد الاستخدام.
- لا يُختار مزود مدفوع أو مورد مكلف تلقائياً خارج الميزانية المعتمدة.

## 11. عقود التكامل

كل موصل يجب أن يعرّف:
- اسم المزود وإصدار المحول.
- نوع المصادقة ومراجع الأسرار.
- العمليات المسموحة.
- مخطط الطلب والاستجابة.
- حدود المعدل والمهلات وإعادة المحاولة.
- سياسة الأخطاء والتراجع.
- متطلبات الخصوصية والاحتفاظ.
- اختبارات اتصال واختبارات سلوك وأمن.
- حالة الاعتماد وبيئة التشغيل.

نجاح اختبار الاتصال لا يعني اعتماد الموصل للإنتاج.

## 12. القرارات الختامية: استيراد المشاريع والتوسع والحوكمة

تُطبق القرارات ADR-024 وADR-026 وADR-027 الواردة تفصيلاً في [القرارات الختامية المعتمدة](15-final-approved-decisions-and-review-gate.md):

- يدعم النظام استيراد مشروع قائم وتحليله في وضع قراءة فقط مفروض تقنياً، مع فصل كامل عن وضع التطوير والتعديل الذي يتطلب موافقة ونقطة استعادة ومراجعة فروقات واختبارات.
- تُضاف التقنيات والمنصات ومزودو الخدمات عبر وحدات/محولات ذات عقود ونسخ وتوافق معلن، وتُختبر في بيئة معزولة قبل تفعيلها.
- تظل الإضافات محكومة بمبدأ أقل صلاحية، ولا تحصل على أسرار أو بيانات خارج نطاقها.
- يخضع كل وكيل لسياسات مركزية؛ ويجب أن يكون سجل التدقيق محمياً من تعديل الوكلاء، مع فصل قرار الاقتراح عن قرار التنفيذ والموافقة.

لا يعني اعتماد قابلية التوسع اعتماد كل تقنية أو إضافة بعينها، ولا يعني دعم تحليل مشروع قائم السماح بتعديله تلقائياً.
