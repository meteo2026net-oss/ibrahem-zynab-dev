# 179 — تدقيق تنفيذ مستودعات Android وتكاملات GitHub/Telegram وخزنة الأسرار

**الحالة:** SOURCE-INSPECTED / NO LIVE INTEGRATION TEST / NO CODE CHANGES  
**Commit baseline:** `1b76824765803370d02bfe537aa35d9bd664e0f4`  
**النطاق:** قراءة ساكنة لطبقة Android repositories؛ لا استدعاء لمزودي خارجيين، ولا اختبار بيانات اعتماد، ولا تعديل تنفيذي.

## 1. النتيجة

توجد طبقة Android تتصل فعلياً بـFirestore في بعض المسارات، لكن عدداً من وظائف التكامل المعروضة لا ينفذ اتصالاً حقيقياً بالمزود. كما أن تنفيذ خزنة الأسرار الحالي لا يحقق ادعاء «Backend-only»: التشفير وفك التشفير يجريان داخل تطبيق Android، ومفتاح AES ثابت مضمن في مصدر التطبيق، ودالة التشفير تعيد النص الأصلي عند حدوث استثناء. هذه مخاطر P0 تمنع استخدام الخزنة لحماية أسرار حقيقية.

## 3. النتائج

### AND-SEC-01 — مفتاح تشفير ثابت مضمن في التطبيق
**التصنيف:** CONFIRMED FROM SOURCE / P0

`CryptoUtils` يبني مفتاح AES من قيمة ثابتة في كود العميل، ثم يستخدم AES/GCM. وجود GCM وIV لا يعالج مشكلة سرية المفتاح: قيمة المفتاح المضمنة قابلة للاستخراج من APK أو المصدر، وبالتالي لا توفر سرية موثوقة بين مستخدمي التطبيق أو أمام من يحصل على الحزمة. لا تكرر قيمة المفتاح في الوثائق أو السجلات أو المحادثات.

**المعالجة:** نقل إدارة المفاتيح والتشفير إلى خدمة موثوقة أو KMS/Secret Manager؛ لا تشارك مفتاحاً ثابتاً بين تثبيتات العملاء. إذا لزم تشفير طرف العميل، فيجب اعتماد مفاتيح منفصلة مشتقة/محمية بمخزن مفاتيح المنصة وبروتوكول تدوير واسترداد واضح، مع عدم جعل ذلك بديلاً عن server-side authorization.

### AND-SEC-02 — فشل التشفير يؤدي إلى إرجاع النص الأصلي
**التصنيف:** CONFIRMED FROM SOURCE / P0

في مسار catch داخل `CryptoUtils.encrypt` يتم إرجاع قيمة الإدخال نفسها عند فشل التشفير. هذا يحول فشل الحماية إلى تخزين محتمل للنص الصريح دون إيقاف العملية أو إظهار فشل آمن.

**المعالجة:** fail closed: أي فشل تشفير يجب أن يوقف التخزين ويعيد خطأً صريحاً؛ لا fallback إلى plaintext مطلقاً. أضف اختباراً يثبت عدم كتابة أي قيمة عند فشل التشفير.

### AND-SEC-03 — فك الأسرار يتم داخل Android وليس في Backend
**التصنيف:** CONFIRMED FROM SOURCE / P0

`SecretsVaultRepository.resolveSecretBackendOnly` يقرأ الوثيقة من Firestore ويستدعي `CryptoUtils.decrypt` داخل التطبيق نفسه. اسم الدالة والتعليق لا يغيران مكان التنفيذ. كما أن `observeSecrets` يجلب وثائق الخزنة إلى التطبيق، بما فيها حقول الوثيقة التي تشمل قيمة مشفرة.

**المعالجة:** لا تمنح تطبيق العميل صلاحية قراءة ciphertext الخاص بالأسرار. اجعل resolve عبر خدمة خلفية موثوقة تتحقق من المستخدم والمشروع والخدمة والوكيل والعملية والمدة، وتسجل الحدث، ثم تستخدم السر في الاتصال المطلوب دون إعادته إلى العميل أو نموذج الذكاء الاصطناعي.

### AND-SEC-04 — التحقق من صلاحيات الوكيل والعملية غير مكتمل في resolver
**التصنيف:** CONFIRMED FROM SOURCE / P1

الدالة تتحقق من `allowedServices` لكنها لا تتحقق من `allowedAgents` أو `allowedOperations` رغم استلام `requestingAgent` ووجود قائمة العمليات في النموذج. كذلك لا يظهر تحقق موثوق من ملكية `projectId` في هذا المسار يتجاوز فلترة `userId`.

**المعالجة:** نقل قرار التفويض إلى backend والتحقق من كل أبعاد grant: user/tenant/workspace/project/service/agent/operation/expiry، مع سجل تدقيق لا يستطيع العميل تعديله.

### AND-INT-01 — عمليات GitHub المعروضة جزئياً محاكاة
**التصنيف:** CONFIRMED FROM SOURCE / P1

في `IntegrationsRepository`:
- `getSampleRepositoriesForAccount` يعيد قائمة مستودعات ثابتة مصطنعة.
- `createCommit` ينشئ SHA عشوائياً ويسجل الحدث، ولا ينفذ Git commit أو push إلى GitHub.
- `createPullRequest` يولد رقم PR عشوائياً ويرجع رابطاً مبنياً نصياً، ولا ينشئ PR عبر GitHub API.
  
لذلك لا يجوز عرض نجاح هذه الإجراءات على أنه نجاح تكامل GitHub حقيقي.

### AND-INT-02 — استقبال Telegram محاكاة محلية
**التصنيف:** CONFIRMED FROM SOURCE / P1

`simulateIncomingTelegramEvent` ينشئ مستند حدث Firestore مباشرةً ويعلّق على أنه محاكاة حدث وارد. لا يثبت وجود webhook server حقيقي أو تحقق توقيع Telegram أو معالجة إعادة الإرسال أو حماية replay أو تحقق ملفات المرفقات.

**المعالجة:** بناء endpoint خلفي موثوق مع تحقق webhook secret/token، منع replay، حدود حجم/نوع المرفق، فحص malware، وإقرار idempotency قبل إدراج الحدث.

### AND-DATA-01 — الكتابة إلى Firestore من العميل تتجاوز حدود الخدمات المؤسسية
**التصنيف:** CONFIRMED ARCHITECTURAL GAP / P1

تتصل repositories مباشرة بمجموعات Firestore، ومنها المشاريع والمهام وسجلات التدقيق وخزنة الأسرار والتكاملات. هذا لا يثبت أن كل مسار يجب أن يمر بخادم، لكنه يعني أن العمليات الحساسة لا تزال تعتمد على قواعد Firestore العميلية الحالية، وهي التي أظهر التدقيق 178 أنها تسمح بتعديل سجلات تدقيق وموافقات وأسرار من العميل.

**المعالجة:** فصل عمليات CRUD العادية ذات النطاق المحدود عن العمليات المميزة. اجعل القرارات، التدقيق غير القابل للعبث، حل الأسرار، إدارة رموز المزود، والـwebhooks عبر خدمات موثوقة ذات صلاحيات ضيقة.

### AND-DATA-02 — عمليات تحديث/حذف المهام لا تمرر تحقق ملكية داخل المستودع
**التصنيف:** CONFIRMED CLIENT-SIDE GAP / P1

`updateTaskStatus` و`deleteTask` يستخدمان معرف المهمة مباشرةً ولا يتحققان محلياً من UID أو أن المهمة تنتمي إلى المشروع الممرر. يجب أن يكون التحقق الحقيقي في القواعد أو backend، ولا يجوز الاعتماد على قيم الواجهة. قواعد Firestore الحالية تتحقق من مالك السجل القديم، لكنها لا تربط `projectId` بعضوية المشروع ولا تمنع تغيير حقول أخرى.

**المعالجة:** فرض الملكية والعضوية على مستوى القاعدة/الخدمة، والتحقق من علاقة المهمة بالمشروع، مع اختبارات مستخدم/مؤسسة أخرى.

## 4. أثر النتائج على التسليم

هذه النتائج تعني أن:
- لا يجوز إدخال رموز GitHub أو Telegram أو كلمات مرور قواعد بيانات حقيقية في خزنة Android الحالية.
- لا يجوز اعتبار وظائف commit/PR/webhook منفذة لمجرد وجود أزرار أو سجل نجاح.
- لا يجوز اعتبار اختبارات CryptoUtils الحالية دليلاً على أمان تشفير الإنتاج؛ فهي تختبر round-trip باستخدام المفتاح الثابت نفسه.
- يجب إغلاق AND-SEC-01..04 قبل أي استخدام حقيقي للأسرار، وAND-INT-01..02 قبل وصف تكامل GitHub/Telegram بأنه فعلي.

## 5. خطة المعالجة

**P0:** إزالة مفتاح التشفير الثابت من العميل؛ إلغاء fallback إلى plaintext؛ نقل إدارة الأسرار وفكها إلى backend/KMS؛ منع قراءة الأسرار المشفرة من تطبيق العميل؛ استكمال authorization على مستوى الخدمة.

**P1:** استبدال GitHub mocks بعميل API حقيقي يعمل عبر OAuth/token broker خادمي؛ بناء Telegram webhook backend؛ فرض project/tenant membership؛ إضافة اختبارات تكامل ضد بيئة اختبار للمزودين وقواعد Firestore Emulator.

**P2:** إضافة contract tests وidempotency/replay tests وaudit immutability tests، مع مراقبة أخطاء التكامل وتجديد الرموز وإبطالها.
