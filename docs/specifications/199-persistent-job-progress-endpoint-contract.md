# 199 — عقد تحديث تقدم المهام المحمية بعقدة التنفيذ

## الحالة
تنفيذ برمجي في Firebase Functions؛ لا يعني وجود عامل تنفيذ فعلي أو أن المهام أصبحت تنفذ تلقائياً.

## نقطة النهاية
`updatePersistentJobProgress` هي HTTP endpoint خاصة بـ IAM (`invoker: private`) وتقبل POST فقط. تتطلب `jobId` و`workerId` و`leaseToken` صالحاً، وتستخدم `verifyAndReadLease` للتحقق من ملكية العقدة وصلاحية المهلة قبل تعديل المهمة.

## قواعد التقدم
- `progress` عدد صحيح من 0 إلى 99؛ لا يسمح بنسبة 100 قبل إنهاء المهمة.
- `currentStepIndex` عدد صحيح غير سالب.
- التقدم أحادي الاتجاه ولا يقبل الرجوع إلى قيمة أقل من المخزنة.
- يحد `message` إلى 500 حرف.
- تُحدّث `progress` و`progressPercent` معاً، مع `heartbeatAt` و`updatedAt`.
- إذا طلب المستخدم الإلغاء، تعيد النقطة 409 مع `job-cancellation-requested` ليوقف العامل عمله ثم يستدعي الإنهاء.

## إنهاء المهمة
- يثبت `finishPersistentJob` قيمة `progressPercent=100` فقط عند النجاح.
- إذا كان الإلغاء قد طُلب قبل الإنهاء، تكون الحالة النهائية `CANCELLED` ويعكس رد HTTP الحالة الفعلية بدلاً من الحالة التي طلب العامل كتابتها.
- تبقى عمليات claim/renew/finish مقيدة بعقدة تملك lease صالحاً.

## ما لم ينجز بعد
- لا يوجد حتى الآن Cloud Tasks dispatcher يلتقط المهام الجديدة.
- لا يوجد worker runtime منشور يستدعي نقاط النهاية أو ينفذ خطوات بناء التطبيقات.
- لا يوجد تكامل موصلات AI server-side أو اختبارات تكامل فعلية لهذه الدورة.
- يلزم اختبار السباقات، انتهاء lease، الإلغاء أثناء التنفيذ، وعدم تراجع التقدم قبل اعتماد الميزة إنتاجياً.

## التحقق
تُشغّل Firebase Functions CI تلقائياً عند دفع تغييرات `functions/**` إلى `main`. لا يعتبر هذا التوثيق نجاحاً للاختبارات؛ يجب تسجيل نتيجة GitHub Actions الفعلية بعد اكتمال التشغيل.
