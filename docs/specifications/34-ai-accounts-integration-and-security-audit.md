# 34 — تدقيق مركز حسابات الذكاء الاصطناعي والتكاملات

**التاريخ:** 2026-11-10  
**النطاق:** `AiAccountsRepository.kt`، `AiAccountsModels.kt`، `firestore.rules`، `firebase-blueprint.json`، ومجموعة `MetraCoreUnitTest.kt`.  
**المنهج:** مراجعة ساكنة للمصدر الحالي؛ لم يُشغّل Firebase Emulator أو تدفق OAuth حي أو Gradle tests.

## 1. النتائج

### AUD-FUNC-005 — OAuth شكلي لا يتضمن تبادل رمز موثق
- **الخطورة:** حرجة وظيفياً إذا عُرض كاتصال حقيقي.
- **الدليل:** `connectOAuthAccount` ينشئ `oauth_tok_` و`oauth_ref_` من UUID محلي، ثم يخزنها ويعين الحالة ACTIVE. لا يظهر طلب authorization code أو token endpoint أو state/PKCE أو تحقق issuer.
- **المطلوب:** عدم إعلان ACTIVE قبل تحقق فعلي؛ تنفيذ OAuth الرسمي لكل مزود أو وسم المسار Demo بوضوح؛ عدم حفظ رموز شكلية كاعتمادات.
- **الحالة:** خلل ظاهر في المسار المفحوص؛ لم يُختبر اتصال حي.

### AUD-FUNC-006 — تحديث وفصل الحساب دون تحقق ملكية صريح داخل المستودع
- **الخطورة:** عالية.
- **الدليل:** `refreshAccountTokens(accountId)` و`disconnectAccount(accountId)` يصلان إلى المستند بالمعرف وحده ولا يتحققان صراحة من userId. كما أن التجديد يمدد تاريخ الانتهاء محلياً ولا يتصل بمزود OAuth.
- **المطلوب:** تحقق ملكية ونطاق على الخادم؛ تجديد فعلي عبر refresh token؛ اختبارات مستخدمين متقاطعين.
- **الحالة:** خلل ظاهر في الكود؛ أثر الوصول محكوم بقواعد Firestore ولم يختبر بالمحاكي.

### AUD-FUNC-007 — ai_accounts غائبة عن قواعد Firestore وBlueprint
- **الخطورة:** عالية.
- **الدليل:** يستخدم المستودع المجموعة في القراءة والإنشاء والتحديث والحذف؛ لا يوجد match لها في `firestore.rules` ولا تعريف لها في `firebase-blueprint.json`.
- **الأثر المحتمل:** الرفض الافتراضي لعمليات العميل. لا تُضف قاعدة عامة لتجاوز الرفض لأن المستند يتضمن رموزاً مشفرة وبيانات حالة وقيود إنفاق.
- **المطلوب:** قرار schema وملكية واضح، ثم قواعد least-privilege واختبارات emulator.

### AUD-FUNC-008 — مؤشرات التكلفة والحصص قيم تهيئة وليست قياسات مثبتة
- **الخطورة:** متوسطة/عالية.
- **الدليل:** تعيين قيم ثابتة مثل spend cap وcurrent cost وquota percent وRPM عند الإنشاء، دون ظهور مصدر billing/usage موثق في المسار.
- **المطلوب:** تمييز الافتراضي عن الفعلي، وإظهار مصدر القياس وتوقيته، وعدم ادعاء حدود مزود لم يتم التحقق منها.

### AUD-TEST-002 — اختبارات لا تثبت حدود أمان حسابات AI
- **الخطورة:** عالية.
- **الدليل:** توجد اختبارات round-trip للتشفير وخزنة الأسرار، لكن لا يظهر اختبار fail-closed أو ملكية متقاطعة أو قواعد ai_accounts/audit_logs ضمن ملف الاختبار المفحوص.
- **المطلوب:** اختبارات سلبية وFirebase Rules Emulator واختبارات OAuth contract.

## 2. ملاحظة على الاختبارات الحالية
وجود اختبارات مثل `testCryptoUtilsEncryptionAndDecryption` و`testSecretsVaultEncryptionAndReferenceSystem` لا يثبت حماية المفتاح الثابت أو أن التشفير يفشل مغلقاً. يجب فصل اختبار صحة الوظيفة عن اختبار الضوابط الأمنية.

## 3. قرارات لا تُفترض تلقائياً
1. هل تبقى `ai_accounts` مجموعة مستقلة أم تُدمج بيانات الاعتماد في Vault؟
2. هل يدعم المنتج OAuth لكل مزود أم API key فقط لبعض المزودين؟
3. ما هو المصدر المعتمد لقياسات الاستخدام والفوترة؟
4. هل تتم كل عمليات تحديث/حذف الحساب عبر Backend فقط؟

## 4. حدود التقرير
- لم تُعدّل ملفات التطبيق أو قواعد Firestore.
- لم تُنفذ اتصالات OAuth أو طلبات مزود حقيقية.
- لم يُشغّل Firebase Emulator أو Gradle.
- النتائج تخص المسارات والملفات المفحوصة ولا تثبت خلو بقية التطبيق من العيوب.

**الخلاصة:** مركز حسابات AI يحتاج فصل بيانات العرض عن حالة الاتصال الفعلية، وإقرار مخطط وقواعد موحدة، واختبارات ملكية وتفويض قبل اعتباره جاهزاً للإنتاج.
