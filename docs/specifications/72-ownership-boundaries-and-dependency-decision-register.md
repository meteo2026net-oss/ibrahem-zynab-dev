# 72 — سجل حسم حدود الملكية والتبعيات لعقود C01–C14

**الحالة:** DERIVED-REVIEW / OWNER-DECISIONS-REQUIRED / NOT-APPROVED / NO-IMPLEMENTATION  
**التاريخ:** 2026-11-15  
**المراجع:** 23 و32 و36 و59–71، وسجل القرارات 56.  
**الغرض:** تحويل المراجعة الموحدة إلى سجل قرارات محدد يمنع تداخل مالك المجال مع الخدمة المشتركة، ويحدد ما يجب اعتماده قبل ERD/API والاختبارات.  
**حدود الوثيقة:** هذه توصيات توحيد مشتقة. لا تعدل المصدر التاريخي ولا تحسم الملكية نيابة عن مالكي المراكز.

## 1. الخلاصة

أظهر التدقيق المقارن أن عبارة «ملكية الأصل/الإعداد/التكامل/الوثيقة» قد تعني أشياء مختلفة: حقيقة المجال، metadata تشغيل الخدمة، binary storage، فهرسة، أو عرضاً مشتقاً. يجب فصل هذه الأنواع صراحةً قبل اعتماد أي schema.

**القرار المقترح الموحد:** لكل مورد حقيقة مجال واحدة (Domain SoR)، ولكل قدرة أفقية سجل تشغيل مستقل (Shared Service SoR)، وتبقى واجهة C14 projection للقراءة. لا يملك المستهلك نسخة قابلة للكتابة من حقيقة منتج آخر. إذا تعذر الفصل داخل خدمة واحدة، يجب أن يظل الفصل واضحاً في API والملكية والضوابط والتدقيق.

## 4. بوابة موحدة لعقد كل API/Event/Approval

قبل اعتماد أي عملية يجب أن يحتوي سجلها على:
1. اسم العقد وإصداره ونوعه Query/Command/Event/Approval/Task.
2. المنتج والمالك الدلالي، والمستهلكون المصرحون، ومالك التشغيل إن كانت خدمة مشتركة.
3. tenant/workspace/project/environment scope بحسب المورد، مع تحقق خادمي لا ثقة في قيم العميل.
4. actor/service identity، action، resource ref، policy decision ref، approval ref عند الحاجة.
5. expectedVersion أو content fingerprint للكتابة/الاعتماد على مورد متغير.
6. idempotency semantics للعمليات القابلة للإعادة، وtimeout/retry/cancel behavior.
7. تصنيف البيانات، purpose، consent/legal basis عند الانطباق، وحقول التنقيح.
8. schema validation، error codes، compatibility/deprecation policy.
9. audit event reference للعمليات الحساسة.
10. provenance للمخرجات/الأحداث: producer، source version، correlation id، occurredAt.
11. اختبارات contract وnegative authorization وcross-tenant.
12. SLA/SLO أو حدود freshness عند الحاجة، مع إبقاء القيم الرقمية غير معتمدة حتى القرار.

لا تفرض هذه القائمة أسماء HTTP paths أو تقنية نقل أو broker أو قاعدة بيانات بعينها.

## 8. فحص الاتساق وحدود الدليل

- C14 يبقى لوحة التحكم الرئيسية، ولا يستحدث مركز تشغيل خامس عشر.
- لا يرفع هذا السجل Zero Trust إلى قرار معتمد.
- لا يضيف خدمات SH-17..SH-20 ولا يدعي استعادة الفصل 157.
- لا يحدد RTO/RPO أو أسعاراً أو عتبات ميزانية رقمية نهائية.
- كل كيانات C08–C14 وعملياتها واختباراتها في 64–70 تظل مشتقة ومقترحة.
- لا توجد في هذه الوثيقة اختبارات منفذة أو مخططات DB/API منشورة.
- يلزم تحديث 36 بعد اعتماد OWN-01..10؛ لا يستبدل تاريخ الوثيقة 36 ولا يعدل دون سجل قرار.

## 9. حالة التسليم

**CONSOLIDATED-OWNER-DECISION-REGISTER / NOT-APPROVED / NO-IMPLEMENTATION.**

الخطوة التالية هي مراجعة المالكين وحسم OWN-01..10 ثم تثبيت قاموس البيانات وعقود الواجهات ومصفوفة الصلاحيات. وبعد اعتماد المواصفات بالكامل، تبقى موافقة بدء البرمجة قراراً مستقلاً.


## 10. حزمة قرارات الاعتماد

أضيفت الوثيقة 76 لتحويل OWN-01..10 وFLD-01..26 إلى قرارات قابلة للاعتماد، مع مالك اعتماد بحسب الدور، والأطراف المستشارة، والتوصية، وشروط القبول، ومخرج الإغلاق. جميع القرارات تظل OPEN حتى تسجيل قرار مالك فعلي؛ ولا يجوز اعتبار هذه الإضافة اعتماداً أو تعديل الوثيقة 36.
