## 2. قرارات تقنية مبدئية قيد المراجعة

ظهر خط أساس مبدئي لخدمات TypeScript/NestJS وPython، PostgreSQL، S3-compatible object storage، pgvector، Redis/Valkey، BullMQ، WebSocket/SSE، OpenTelemetry، GitHub Actions، OIDC/OAuth2 مع Keycloak كخيار، مدير أسرار وسجل تدقيق. هذه القائمة لا تُعامل كاعتماد نهائي لكل منتج أو إصدار؛ راجع [خط الأساس التقني](10-technical-baseline-and-open-choices.md).

## 3. قرارات تحتاج مراجعة أو تفصيلاً

- التقنية النهائية لكل خدمة خلفية وقاعدة بيانات للمصمم نفسه.
- دور التطبيق Android/Kotlin الحالي وما يمكن إعادة استخدامه.
- خطة انتقال من المكونات الحالية إلى البنية المستهدفة إن لزم.
- اختيار محرك تدفقات قابل للتبديل وعقده.
- قائمة المحولات المدعومة في الإصدار الأول.
- مزود التخزين والنسخ الاحتياطي وموقع البيانات.
- سياسة الاحتفاظ والحذف والخصوصية حسب الأسواق المستهدفة.
- حدود التكلفة والميزانيات الافتراضية.
- أهداف RTO/RPO ومستويات الخدمة.
- تفاصيل الوظائف والاختبارات الأصلية لكل مركز.
- تفاصيل عقود APIs والأحداث.

## 6. مصفوفة التتبع المطلوبة

يجب أن تتوفر سلسلة تتبع لكل متطلب:

`GOAL → BR → REQ → FUNC → SCR / DATA / API / PERM → TEST → EVIDENCE → RELEASE`

- GOAL: هدف المنتج.
- BR: هدف العمل.
- REQ: المتطلب.
- FUNC: الوظيفة.
- SCR: الشاشة.
- DATA: الكيان أو البيانات.
- API: العقد أو العملية.
- PERM: الصلاحية.
- TEST: الاختبار.
- EVIDENCE: دليل التنفيذ والنتيجة.
- RELEASE: الإصدار الذي يحتوي الوظيفة.

لا يُقبل متطلب حرج بلا اختبار ودليل نتيجة.

## 7. قواعد تحديث السجل

- لا يُحوّل PROPOSED إلى APPROVED دون قرار واضح.
- لا يُحذف قرار قديم؛ يوسم SUPERSEDED ويرتبط بالقرار البديل.
- لا يُعدّل متطلب معتمد بصمت؛ ينشأ Change Request وتحليل أثر.
- كل تغيير يحدد الملفات والبيانات والعقود والاختبارات المتأثرة.
- لا يُعتمد توثيق مختصر على أنه مواصفة تنفيذ كاملة.
