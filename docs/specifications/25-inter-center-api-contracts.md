# 25 — عقود الاتصال والتكامل بين المراكز الأربعة عشر

**الحالة:** RECOVERED_DETAILED / CONTRACT SCHEMAS PENDING  
**المصدر:** الفصل 135 من ملف التصدير 2026-11-10-export-part-04.txt.  
**الحدود:** أسماء العمليات والمصفوفة مستعادة من المصدر. لا توجد هنا APIs منشورة أو schemas مكتملة؛ أسماء العمليات أمثلة مقترحة في الفصل الأصلي.

## 1. الهدف

منع الترابط الداخلي المباشر بين المراكز، وتوحيد شكل الطلبات والاستجابات والأخطاء والصلاحيات والمالك والمهل وإعادة المحاولة والإصدارات والأحداث الناتجة.

## 2. أنواع العقود

| النوع | الاستخدام | المالك |
|---|---|---|
| Query Contract | قراءة بيانات مركز | المركز المالك للبيانات |
| Command Contract | طلب تنفيذ عملية | المركز المنفذ |
| Event Contract | إعلان حدث وقع | الخدمة/المركز المنتج |
| File Contract | مشاركة أصل مع صلاحياته | File Service ومالك المحتوى |
| Workflow Contract | تدفق متعدد المراكز | Task/Workflow orchestration مع مراكز المجالات |
| Approval Contract | طلب قرار أو موافقة | Approval Service مع سياسة المجال |
| Streaming Contract | متابعة التقدم والنتائج الحية | الخدمة المالكة للمهمة |

## 3. سياق الطلب الموحد المستعاد

كل طلب بين الخدمات يحمل عند انطباقه:
- requestId
- correlationId
- organizationId
- projectId
- actor.type وactor.id
- action
- contractVersion
- payload

مثال توضيحي مستعاد في الفصل:

    {
      "requestId": "request-123",
      "correlationId": "workflow-456",
      "organizationId": "org-123",
      "projectId": "project-123",
      "actor": { "type": "user", "id": "user-123" },
      "action": "design.generate-preview",
      "contractVersion": "1.0",
      "payload": {}
    }

**قاعدة أمنية:** الخدمة المستقبلة تتحقق من السياق والصلاحيات بنفسها. وجود organizationId أو projectId في الطلب لا يثبت أن الفاعل يملكهما.

## 5. نماذج عمليات مراكز المجال المستعادة

### C02 التصميم — الفصل 135.5

عمليات مقترحة:
- createDesignWorkspace
- getDesignDocument
- validateDesignDocument
- generatePreview
- submitDesignForApproval
- getApprovedDesignVersion

مدخلات: project id، design document id، document version، operation type، device context للمعاينة.

مخرجات: task id، status، validation report، preview reference، approved version id عند توفره.

قاعدة: لا يستخدم C05 تصميماً غير معتمد كمصدر رسمي للتوليد النهائي، إلا إذا كان الطلب صراحةً لمعاينة تجريبية.

## 6. قواعد توافق العقود — الفصل 135.10

- لا تغيير غير متوافق دون إصدار جديد.
- لا حذف لحقل يستخدمه مستهلك معتمد دون خطة انتقال.
- الحقول الجديدة اختيارية عند الإمكان.
- توثيق الحالات والقيم المقبولة.
- توفير أمثلة الطلبات والاستجابات.
- اختبارات توافق آلية.
- تسجيل الخدمات المستهلكة لكل عقد.
- سياسة واضحة لإيقاف العقود القديمة وإزالتها.

## 9. ما يلزم قبل اعتماد العقود

لكل عملية يجب استكمال:
1. HTTP method/path أو message topic الفعلي.
2. JSON Schema أو protobuf/schema registry contract.
3. required/optional fields وvalidation/limits.
4. error codes موحدة وretryability.
5. authentication/authorization scopes.
6. idempotency/correlation/trace behavior.
7. pagination/rate limits/timeouts.
8. event versioning وdelivery guarantees.
9. owner/provider/consumer list.
10. contract tests وcompatibility policy.
11. data classification وretention.
12. أمثلة success/failure وevidence.

**الخلاصة:** الفصل 135 مستعاد تفصيلياً بما يكفي لبناء كتالوج عقود أولي ومصفوفة اعتماديات. لا تزال schemas وendpoints واختبارات التشغيل الفعلية بحاجة إلى استكمال، ولم يتم تنفيذ APIs في هذا العمل.
