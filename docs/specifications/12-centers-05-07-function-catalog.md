# 12 — كتالوج وظائف المراكز C05 وC06 وC07

**المصدر:** تفاصيل وظائف موسعة مستعادة من مواصفات العمل السابقة.  
**ملاحظة:** أسماء الوظائف ومعرفاتها محفوظة؛ بعض المدخلات والمخرجات التفصيلية لم تُستعد في هذا الملخص، ولذلك لا تُستكمل بالتخمين.

## C05 — مركز البرمجة

### دورة العمل

1. استلام المتطلبات والتصميم والبيانات المعتمدة.
2. بناء نموذج وسيط IR يمثل البنية والسلوك دون ربطه بإطار واجهة واحد.
3. اختيار المحول والتقنية ضمن السياسة المعتمدة.
4. توليد الملفات أو تعديلها مع تحديد مصدر كل تغيير.
5. حماية التعديلات اليدوية وكشف التعارضات قبل الكتابة.
6. تشغيل الفحوص داخل Sandbox معزول.
7. مراجعة الأخطاء والاعتماديات والأمن والتراخيص.
8. حفظ التغييرات في GitHub عبر فرع وCommit واضح.
9. إنشاء Pull Request للمراجعة عند الحاجة.
10. عدم الدمج أو التسليم قبل نجاح الاختبارات والموافقات المطلوبة.

### المدخلات والمخرجات

**المدخلات:** معرف المشروع، المتطلبات المعتمدة، إصدار التصميم، مخطط البيانات، التقنية والمحول، إعدادات البيئة، التغييرات اليدوية، سياسة الاعتماديات، والصلاحيات.

**المخرجات:** ملفات كود، IR، تقارير التحويل، قائمة التبعيات، نتائج البناء والاختبار، تقارير الأخطاء والأمن والتراخيص، diff، Commit/PR، وقرار اعتماد أو رفض.

### الصلاحيات

- مالك المشروع: الاطلاع والموافقة على المخرجات والقرارات عالية الأثر.
- المطور: تحرير وتشغيل Sandbox وإدارة الفروع ضمن التفويض.
- وكيل البرمجة: اقتراح/تنفيذ تغييرات محددة داخل نطاق المهمة المصرح بها.
- المراجع: مراجعة diff والاختبارات والمخاطر.
- مسؤول الأمن: مراجعة نتائج الفحص والأسرار والتبعيات.
- لا يدمج الوكيل التغييرات أو ينشرها دون التفويض والموافقات المحددة.

### اختبارات القبول المسجلة

`C05-AT-01` إلى `C05-AT-20`. وتشمل المجالات المستعادة: تهيئة البيئة، تحرير الملفات، التوليد من التصميم والمتطلبات، التتبع، المحولات، الاعتماديات، التعديل باللغة الطبيعية، حماية التعديلات اليدوية، المزامنة، Sandbox، تحليل الأخطاء، الأسرار، التراخيص، GitHub، الدمج، والتسليم. يجب استعادة النص الأصلي لكل حالة قبل اعتمادها كخطة اختبار تنفيذية.

### نموذج البيانات

عائلة `code_*` وتشمل على الأقل سجلات المشاريع البرمجية والملفات والتغييرات وIR والمحولات وعمليات التوليد والاعتماديات ونتائج البناء والفحوص وطلبات المراجعة والتسليم. يجب استعادة أسماء الجداول والحقول الكاملة من الفصل الأصلي.

### دورة حياة المهمة

الحالات الأساسية:

`CREATED → PLANNED → ASSIGNED → RUNNING → VALIDATING → REVIEW_REQUIRED → COMPLETED`

حالات إضافية:
`BLOCKED`, `WAITING_FOR_APPROVAL`, `FAILED`, `CANCELLED`, `RETRY_PENDING`, `SUSPENDED`.

يجب توثيق شروط الانتقال، المالك، وقت البدء والانتهاء، سبب التوقف، نقاط التحقق، وعدد المحاولات لكل حالة.

### مبادئ التشغيل

- Orchestrator منسق وليس صاحب صلاحيات مطلقة.
- فصل الوكيل عن المهارة والأداة والصلاحية.
- لكل مشروع سياق وذاكرة معزولان.
- لا يتجاوز الوكيل الموافقات أو الميزانية.
- لا تعتبر مخرجات الوكيل صحيحة قبل التحقق والمراجعة.
- يجب دعم الإيقاف والاستئناف وإعادة المحاولة بأمان.
- يجب تسجيل المزود والنموذج والتكلفة والمدة والنتيجة.
- لا يستطيع الوكيل تغيير سجل التدقيق أو منح نفسه صلاحية.
- يجب فصل اقتراح AI عن محرك التنفيذ.

### المدخلات والمخرجات

**المدخلات:** هدف المهمة، المشروع والنطاق، المتطلبات، الوكيل ومهاراته، الأدوات المسموحة، السياسات، الميزانية، الموعد، والسياق المصرح به.

**المخرجات:** خطة تنفيذ، تعيينات، مخرجات مرحلية، طلبات موافقة، سجلات استخدام، نتائج تحقق، تقارير تكلفة، حالة مهمة، وقرار اكتمال أو فشل.

### الصلاحيات

- مدير فريق AI: إدارة الوكلاء والمهارات والسياسات ضمن صلاحياته.
- مالك المشروع: اعتماد العمليات والنتائج عالية الأثر.
- الوكيل: تنفيذ مهمة محددة بالأدوات والنطاق المسموح.
- مسؤول الأمن: مراجعة الصلاحيات والبيانات والأدوات.
- المدقق: قراءة سجل التدقيق.
- لا يجوز للوكيل الموافقة على عمليته الحساسة أو توسيع صلاحياته.

### اختبارات القبول المسجلة

`C06-AT-01` إلى `C06-AT-20`. تغطي إنشاء وكيل متخصص، إسناد المهارات والأدوات، إسناد المهام، العزل، التفويض، التنسيق، حدود الميزانية، الموافقات، الإيقاف والاستعادة، التدقيق، والتحقق من النتائج. يجب استعادة نصوص الحالات الأصلية قبل تحويلها إلى اختبارات تنفيذية نهائية.

### نموذج البيانات

عائلة `ai_*` وتشمل الوكلاء والمهارات والأدوات والتفويضات والمهام والخطط والتعيينات والذاكرة والمزودين والسياسات والاستهلاك والنتائج والموافقات وسجلات التدقيق والتقييم.

### دورة حياة العيب

`OPEN → TRIAGED → ASSIGNED → IN_PROGRESS → FIXED → RETESTING → VERIFIED → CLOSED`

حالات إضافية:
`REJECTED`, `DUPLICATE`, `DEFERRED`, `WONT_FIX`, `REOPENED`.

### قواعد الجودة

- كل اختبار يرتبط بمتطلب أو خطر أو تغيير.
- يجب حفظ بيئة التنفيذ وإصدار التطبيق والبيانات والنتيجة.
- لا تُقبل نتيجة ناجحة دون دليل قابل للمراجعة.
- لا تجتاز بوابة الجودة إذا بقي شرط إلزامي غير مستوفى.
- الاستثناء يحتاج سبباً ومالكاً وموافقة ومدة صلاحية.
- إعادة الاختبار مطلوبة بعد الإصلاح.
- اعتماد الاختبار لا يعني موافقة النشر؛ قرار النشر منفصل.

### الصلاحيات

- مدير الجودة: إنشاء الخطط وتنفيذها وإدارة العيوب والاعتماد ضمن التفويض.
- المطور: تشغيل الاختبارات وإصلاح العيوب وتسجيلها.
- وكيل الاختبار: تنفيذ الاختبارات وتسجيل النتائج والعيوب، ولا يغير حالة العيب افتراضياً.
- مسؤول الأمن: مراجعة نتائج الأمن ضمن نطاقه.
- المراجع: مراجعة الأدلة والعيوب وتغيير حالتها ضمن التفويض.
- تجاوز بوابة الجودة يتطلب استثناءً موثقاً وموافقة صريحة.

### اختبارات القبول المسجلة

`C07-AT-01` إلى `C07-AT-22`. تغطي الخطط والحالات والتتبع، Unit/Integration/UI/E2E/API/DB/Security/Performance/Compatibility/Accessibility/Offline-Sync/Regression، وإدارة العيوب والتقارير وبوابات الاعتماد. النصوص الكاملة لكل حالة تحتاج استعادة قبل اعتماد خطة التنفيذ.

### نموذج البيانات

عائلة `qa_*` وتشمل خطط الاختبار والحالات والارتباط بالمتطلبات والتشغيلات والنتائج والأدلة والعيوب والاستثناءات وتقارير الجودة وقرارات البوابة.

## قاعدة مشتركة للمراكز الثلاثة

لا تعتبر وظيفة جاهزة للتنفيذ لمجرد وجود اسمها. يجب استكمال مدخلاتها ومخرجاتها وأخطاءها وصلاحياتها وكياناتها وعقودها واختبارات قبولها. كما يجب أن يكون لكل تغيير مصدر ومتطلب ومالك وموافقة عند الحاجة.
