## 2. حدود مسؤولية C11

C11 يملك دورة حياة الإصدار المنشور للتطبيق: تعريف إعدادات build profile وpipeline على مستوى المشروع، إنشاء release candidate، ربط artifact بالمصدر والبصمة والأدلة، إدارة طلب النشر والترقية بين البيئات، تسجيل نتيجة النشر، وتنسيق التراجع والتحقق بعد النشر.

لا يعني ذلك أن C11 يملك كل التنفيذ أو المحتوى المرتبط بهذه الدورة:

| المجال | المالك/الخدمة | الحد الواجب الحفاظ عليه |
|---|---|---|
| مصدر الكود وتغييرات البرمجة | C05 | C11 يستهلك مرجع المصدر وبصمته ولا يملك محتوى الكود |
| ملفات المشروع والوسائط | C08 | C11 يحتفظ بمراجع artifacts؛ لا ينقل ملكية الملفات أو محتواها |
| اختبارات الجودة | C07 | C07 يملك تعريف الاختبارات ونتائجها؛ C11 يستهلك بوابة الجودة |
| بيانات ومخططات وترحيلات المجال | C04 ومالك المجال | C11 ينسق فحوص التوافق ولا يقرر دلالات البيانات أو ينفذ rollback غير آمن |

| metadata وإصدارات الموارد/change sets | SH-10 | لا يملك حالة الإصدار المنشور أو promotion/rollback الخاصة بـC11 |
| قياس الاستخدام والتكلفة | SH-11 | يجمع القياس؛ لا يخترع الأسعار أو حدود الميزانية |

| OP-C11-165 | requestRollback | طلب تراجع مع الهدف والأثر وخطة البيانات | موافقة حسب الأثر وفحص migrations والنسخ |
| OP-C11-166 | getReleaseStatus | قراءة دورة حياة الإصدار والأدلة | ACL وإظهار مصدر الحالة وتوقيتها |

### 3.1 تمييز الطلب والقرار والتنفيذ

- requestBuild وdeployRelease وrunPostDeployChecks هي طلبات/أوامر مجال، بينما تنفيذ المهام ومحاولاتها يقع ضمن SH-08.
- submitReleaseForApproval ينشئ طلب موافقة؛ لا يمنح الموافقة.
- approveRelease هو فعل قرار مجال مرشح، ويجب أن يُنفذ ضمن SH-03 مع فصل صاحب القرار عن مقدم الطلب، وأن يُربط بالـcandidate hash والبيئة والأدلة.
- deployRelease لا يُستدعى إلا بعد تحقق صلاحية الموافقة وتطابقها مع العملية الحالية.
- requestRollback لا يعني أن التراجع قد اكتمل؛ لا تُعلن الحالة النهائية قبل نتائج التنفيذ والتحقق من سلامة البيانات والخدمة.

## 9. القرارات المفتوحة التي تمنع اعتماد C11

1. حسم ملكية validateBuildConfiguration مقابل OP-C05-081 وبيان علاقتها بـvalidateBuildProfile.
2. اعتماد حدود SH-08 في تنفيذ build/deployment/rollback jobs، وتحديد event producer لكل حدث.
3. تحديد مالك artifact registry ومخزن الملفات وسياسة الاحتفاظ والتشفير والتوقيع.
4. تحديد آلية provenance وattestation وSBOM والتراخيص ومصادر أدوات البناء؛ لا يُفرض مزود محدد.
5. تحديد بيئات lifecycle وقواعد promotion وفصل الواجبات ونوافذ النشر.
6. اعتماد release channels وسياسة versioning وhotfix وemergency release.
7. تحديد شروط إبطال approval وربطها بالبصمة والبيئة والأدلة.
8. تحديد سياسة migration compatibility وrollback/roll-forward وخطة البيانات.
9. تحديد SLO وRTO/RPO وقيم recovery الفعلية مع مالكي SH-14/15؛ لا توجد أرقام معتمدة في هذه الحزمة.
10. اعتماد سياسة قياس التكلفة وحدود التنبيه/الإيقاف مع SH-11؛ لا تُعامل نسب الميزانية المقترحة كقرار.
11. اعتماد schemas للطلبات والاستجابات والأخطاء والصلاحيات والإصدارات وevent envelope.
12. ربط كل عملية/حدث/موافقة باختبار أصلي أو اعتماد اختبار محلي بعد مراجعة المالك.
13. اعتماد سياسات عزل tenant ومنع نقل artifact أو logs أو approvals بين المؤسسات.
14. اعتماد صلاحيات المستخدم والمراجع ومالك البيئة ومسؤول المنصة وAI agent ومبدأ الفصل بين الطلب والقرار والتنفيذ.

- فصل 135.9 يتضمن موضع validateBuildConfiguration المتعارض، ويجب الاحتفاظ به كقرار مفتوح.
- لا توجد في هذه الحزمة نتائج تشغيل build أو deployment أو rollback أو restore أو CI.

## 11. معيار إغلاق C11

لا ينتقل C11 إلى APPROVED أو READY-FOR-IMPLEMENTATION حتى تتحقق جميع الشروط:
- حل تعارض العملية وتوقيع مالكي C05/C11.
- اعتماد عقد C11 والكيانات والحقول وSoR.
- اعتماد مصفوفة العمليات والأحداث والموافقات والصلاحيات.
- اعتماد schemas للأحداث وواجهات SH-08/03/10/11/14/15.
- اعتماد بوابات release/deployment/rollback وسياسات artifact.
- ربط الاختبارات بمعرفات موثوقة، وتشغيلها في بيئة معتمدة، وإرفاق نتائجها.
- إغلاق مخاطر الأمن والخصوصية والعزل والتدقيق.
- اعتماد قيم التشغيل والتعافي والتكلفة من أصحاب القرار.
- مراجعة المالك وإصدار قرار قبول موثق.

**الحكم النهائي:** C11 أصبح موثقاً في حزمة تتبع تفصيلية أولية، لكنه ما زال NOT APPROVED / NOT IMPLEMENTED. هذه الوثيقة لا تسمح ببدء البرمجة ولا تثبت جاهزية البناء أو النشر.
