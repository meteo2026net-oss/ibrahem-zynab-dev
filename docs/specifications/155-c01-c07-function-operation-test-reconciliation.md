## 4. تسوية اختبارات القبول

1. يحتوي المصدر B-01..B-07 على 130 معرف قبول فريداً وفق 141 و143.
2. يحتوي 143 على 15 حالة فقط لها نتيجة متوقعة منفصلة في جدول المصدر؛ أما 115 حالة فموصوفة بسيناريو دون نتيجة متوقعة مستقلة. لا يجوز اختراع نتيجة متوقعة ونسبتها للمصدر.
3. جميع المعرفات في 143 NOT EXECUTED؛ لا يوجد run ID أو build hash أو environment أو evidence يثبت نجاحها.
4. عائلات DRAFT-AT في 97/80 ليست بديلاً عن معرفات Cxx-AT المصدرية، ولا يوجد crosswalk exact معتمد بين المجموعتين.
5. تشابه موضوع الاختبار مع وظيفة أو عملية لا يكفي لإثبات Operation→Test. يلزم لكل رابط: test ID ثابت، العملية/الحدث المستهدف، preconditions، actor/tenant scope، input/fixture، expected result، negative/failure cases، evidence contract، ومالك مراجعة.
6. يجب الاحتفاظ بمعرفات المصدر كما هي؛ يمكن إضافة aliases مشتقة بعد موافقة المالك فقط، دون إعادة ترقيم أو إسقاط.

## 5. أحداث المجال

يضم سجل 100 عدد 51 حدثاً للمراكز C01–C07. السجل يصف الأسماء بوصفها SOURCE-RECOVERED ضمن العقود/المصادر الوسيطة، لكن حقول Qualified OWN وDomain SoR لا تزال TBD، واختبارات EVT-96-T01..12 عائلات عامة.

**نتيجة المطابقة:** 0/51 روابط Event→Test exact مثبتة. لا يجوز اعتماد producer أو Domain SoR من مجرد اسم الحدث أو مركزه. الإغلاق يتطلب لكل حدث تحديد producer الفعلي، مالك المجال، schema/version، trigger/transaction boundary، idempotency/correlation، consumer contract، privacy/retention، واختباراً مفرداً مع evidence.

## 6. الموافقات

يضم سجل 98 اثني عشر نوع موافقة للمراكز C01–C07، وجميعها OWNER REVIEW. لا يثبت وجود workflow أو صلاحية تشغيلية.

**فجوة C07 الحرجة:** APR-C07-02 هو اعتماد استثناء الجودة (approveQualityWaiver)، بينما OP-C07-118 هو requestQualityWaiver، أي طلب الاستثناء لا قرار اعتماده. لا يجوز اعتبار عملية الطلب بديلاً عن عملية القرار. يلزم تحديد عملية القرار، دور المعتمد المستقل، صلاحية الاستثناء ومدته ونطاقه، شروط الرفض/الإلغاء، وربطه بـSH-03 والتدقيق.

لا يعيّن هذا المستند مالكي قرارات أو موافقين نيابة عن المستخدم.

## 8. بوابة الجودة قبل اعتماد المواصفات

لا يُعلن إغلاق التتبع إلا عند تحقق جميع الشروط التالية:
- لا توجد وظيفة أو عملية بلا تصنيف صريح ومبرر؛ أي عنصر غير مربوط يبقى OPEN مع مالكه.
- كل علاقة وظيفة↔عملية لها قرار مالك، وليست مجرد تشابه دلالي.
- كل عملية وكل حدث له اختبار مفرد أو قرار موثق بعدم الحاجة إلى اختبار مستقل مع مبرر.
- لكل اختبار تعريف قابل للتنفيذ وexpected result ومجموعة أدلة.
- كل موافقة لها owner/approver وpermission وresource version/hash وexpiry/revoke semantics واختبار.
- لا توجد قيم TBD في Qualified OWN وDomain SoR وAPI owner التي تتطلب قراراً.
- جميع الاختبارات المنفذة مرتبطة بإصدار/commit/build وبيئة ونتائج فعلية؛ لا تستخدم SPECIFIED أو NOT RUN كحالة PASS.
- تتم مراجعة التناقضات المعروفة، ومنها OP-C05-081، دون تعديل صامت للمصدر التاريخي.

## 9. الحكم النهائي

هذه التسوية **تقدم تدقيقي فعلي**: جمعت جرد المصدر والعمليات والقبول والأحداث والموافقات في مصفوفة واحدة، وثبتت الفجوات المتقابلة (9 وظائف و7 عمليات) ومنعت الخلط بين معرفات المصدر والاختبارات المشتقة. لكنها لا تغلق الموافقات ولا تحول المرشحات إلى عقود معتمدة.

**الحالة الحالية:** SPECIFICATION TRACEABILITY INCOMPLETE / OWNER REVIEW REQUIRED / TESTS NOT RUN / CODING NOT AUTHORIZED.

لا تعديل على كود التطبيق أو قاعدة البيانات أو API أو إعدادات البناء. اعتماد المواصفات النهائية وموافقة بدء البرمجة بوابتان منفصلتان، وتبقيان مطلوبتين قبل أي تنفيذ برمجي.
