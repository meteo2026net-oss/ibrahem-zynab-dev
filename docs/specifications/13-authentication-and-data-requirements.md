# 13 — متطلبات الهوية والمستخدمين والصلاحيات والبيانات

هذه المتطلبات عابرة للمراكز، ويجب تنفيذها عبر خدمات مشتركة مع بقاء ملكية كل نطاق واضحة.

## 1. نظام الهوية والدخول

اعتمد المستخدم نظام دخول ومستخدمين وصلاحيات شاملاً، يدعم:
- البريد الإلكتروني.
- رقم الهاتف.
- Google.
- Apple.
- الدخول دون حساب عندما تسمح طبيعة التطبيق والسياسة بذلك.

يجب فصل تسجيل الدخول عن تفويض الوصول. نجاح المصادقة لا يعني أن المستخدم يملك صلاحية فتح مشروع أو بيانات أو إجراء معين.

## 2. إدارة الحسابات

يشمل النطاق الوظيفي:
- إنشاء الحساب والتسجيل.
- التحقق من البريد أو الهاتف عند الحاجة.
- تسجيل الدخول والخروج.
- استعادة الوصول/الحساب.
- إدارة الجلسات والأجهزة.
- إيقاف الحساب أو تعطيله.
- حذف الحساب وفق سياسة الاحتفاظ والالتزامات.
- ربط وفصل طرق الدخول الخارجية وفق ضوابط التحقق.
- إدارة الملف الشخصي وتفضيلات اللغة والمظهر.

## 3. الأدوار والصلاحيات

- أدوار جاهزة وأدوار مخصصة.
- صلاحيات على مستوى الصفحات.
- صلاحيات على مستوى العناصر أو المكونات عند الحاجة.
- صلاحيات على البيانات والسجلات.
- صلاحيات على الإجراءات والعمليات.
- إعداد بسيط أو متقدم حسب طبيعة التطبيق.
- معاينة تجربة التطبيق وفق الدور.
- إدارة أعضاء المؤسسة ومساحة العمل والمشروع.

يجب تطبيق الصلاحيات في الخادم والبيانات، لا الاكتفاء بإخفاء عناصر الواجهة.

## 4. نموذج التفويض

كل قرار وصول يجب أن يراعي:
- هوية الفاعل.
- عضويته في المؤسسة/مساحة العمل/المشروع.
- الدور الفعال.
- نطاق المورد المطلوب.
- الإجراء المطلوب.
- حالة المورد.
- السياسات المفروضة.
- الموافقة المطلوبة إن كانت العملية حساسة.

يجب أن تكون الصلاحيات قابلة للمراجعة والتدقيق، مع سجل للتغييرات.

## 5. متطلبات قاعدة البيانات المرئية

اعتمد المستخدم إدارة بيانات متكاملة تشمل:
- مصمم قاعدة بيانات مرئي دون الحاجة إلى كتابة SQL لكل عملية أساسية.
- إنشاء الجداول والحقول والعلاقات.
- تحديد أنواع البيانات والقيود.
- ربط Firebase وSupabase وواجهات APIs وقواعد بيانات أخرى.
- مزامنة البيانات.
- دعم العمل دون اتصال عند ملاءمة التطبيق.
- اقتراح بنية البيانات مع شرح الأسباب.
- حماية الصلاحيات والتحقق والأسرار.

لا يعني الدعم المذكور أن كل مزود أو محرك قد اعتُمد للتنفيذ في الإصدار الأول؛ يجب اختيار قائمة الموصلات المدعومة وتوثيق إصداراتها.

## 6. قواعد سلامة البيانات

- فصل بيانات المصمم عن بيانات التطبيقات المنشأة.
- عزل المؤسسات والمشاريع على مستوى الخادم.
- التحقق من المدخلات والقيود في الخادم.
- إدارة migrations وإصدارات المخطط.
- عدم افتراض أن التراجع عن migration يعيد البيانات المحذوفة.
- عدم تغيير بيانات الإنتاج دون موافقة.
- اختبار النسخ الاحتياطي والاستعادة.
- تسجيل مصدر البيانات ومالكها وتاريخ تعديلها.
- حماية الأسرار وعدم وضعها في الكود أو المستندات أو سجلات التطبيق.

## 7. Offline & Sync

عند تفعيل العمل دون اتصال:
- تحديد البيانات المسموح تخزينها محلياً.
- تحديد مدة الاحتفاظ المحلي والتشفير.
- تعريف سياسة حل التعارضات.
- منع تكرار عمليات الكتابة بعد عودة الاتصال.
- إظهار حالة المزامنة للمستخدم.
- توثيق العمليات الفاشلة وقابلية إعادة المحاولة.
- عدم مزامنة البيانات التي لم يعد المستخدم مخولاً للوصول إليها.

## 8. اختبارات قبول أساسية

- IAM-AT-01: تسجيل الدخول بالبريد وفق سياسة التحقق.
- IAM-AT-02: تسجيل الدخول بالهاتف وفق سياسة التحقق.
- IAM-AT-03: تدفق الدخول عبر مزود خارجي بعد التحقق من الهوية.
- IAM-AT-04: منع حساب غير مخول من قراءة مشروع آخر.
- IAM-AT-05: تطبيق دور مخصص على الصفحة والبيانات والإجراء.
- IAM-AT-06: منع الوصول إلى API حتى لو كانت الصفحة ظاهرة.
- IAM-AT-07: استعادة الحساب دون كشف معلومات حساسة.
- IAM-AT-08: إبطال الجلسات عند تعطيل الحساب وفق السياسة.
- IAM-AT-09: عزل مؤسستين في التخزين والاستعلام.
- IAM-AT-10: التحقق من صلاحية المستخدم عند المزامنة بعد عودة الاتصال.
- IAM-AT-11: منع تكرار عملية كتابة بعد إعادة المحاولة.
- IAM-AT-12: تسجيل تغييرات الأدوار والصلاحيات في سجل التدقيق.

هذه حالات قبول تأسيسية مستحدثة لتوضيح نطاق الاختبار، وليست ادعاءً بأنها أرقام الاختبارات الأصلية في الفصول السابقة.
