# 166 — سجل إغلاق تعارضات القرارات الأمنية والتكلفة واللوحة والتعافي

**التاريخ:** 2026-11-16  
**الحالة:** SOURCE-BASED DECISION RECONCILIATION / DERIVED / OWNER REVIEW REQUIRED / NOT APPROVED / NOT IMPLEMENTED.  
**المصادر المباشرة:** 83 و87 و89 و135 و137 و138 و139، مع الفصول 158–162 من Export 07 و141–143 من Export 06.  
**الغرض:** توحيد بوابات القرار ومنع تحويل نصوص متعارضة أو معرفات ملتبسة أو أرقام أولية إلى متطلبات تنفيذية دون موافقة صريحة.

## 1. الحكم التنفيذي

توجد أربع مجموعات إغلاق مستقلة:

1. **Zero Trust:** تعارض مصدرّي بين الصياغة الإلزامية في 158.7 وبين إدراج قرار اعتماد Zero Trust ضمن المقترحات في 158.9 و160. لا يوجد دليل موافقة مستقل كافٍ وفق سجل 56/89.
2. **COST/DASH namespaces:** المعرفات نفسها مستخدمة للاختبارات والقرارات. هذا تصادم موثق في المصدر 141–143 كما أعيدت مطابقته في 137.
3. **التكلفة والميزانية:** SH-11 موصوفة، لكن المالك التشغيلي النهائي ومرجع الأسعار/القياس والعملة والتسوية وعتبات الإنفاق وموافقات الميزانيات لم تعتمد.
4. **الاستمرارية والتعافي:** مبادئ المراقبة والنسخ والاستعادة موثقة، لكن لا توجد أهداف رقمية معتمدة لـRTO/RPO/SLO/freshness، ولا دليل تنفيذ لاختبارات الاستعادة.

لا تعني هذه الوثيقة اعتماد أي قرار من هذه المجموعات؛ إنها تسوية حالة ومصفوفة أعمال إغلاق.

## 2. Zero Trust: الفصل بين مبادئ الأمن والقرار المعماري

### 2.1 ما ثبت

| المرجع | المضمون | الحالة التي يجوز إثباتها |
|---|---|---|
| 158.7 | صياغة Zero Trust ضمن متطلبات/مبادئ الأمن المعماري | نص مصدر موجود |
| 158.9 | SEC-REV-01 ضمن قرارات المراجعة المقترحة | قرار اعتماد مفتوح |
| 160 / DEC-SEC-010 | Zero Trust مصنف PROPOSED / CONFLICT | مقترح متعارض |
| 56 و89 | لا يوجد دليل موافقة مستقل كافٍ لترقية القرار | لا اعتماد مثبت |

### 2.2 لا تخلط بين ثلاث طبقات

- **ضوابط أمنية أساسية:** التحقق من الهوية والصلاحية والنطاق، least privilege، فصل الواجبات، التدقيق، حماية الأسرار، عزل المستأجرين، وعدم منح الوكلاء سلطة ذاتية. تبقى كل قاعدة مصدرية/معتمدة في موضعها ولا تحتاج إلى تسمية Zero Trust كي تكون واجبة.
- **اختيار إطار معماري:** هل يعتمد المشروع Zero Trust كإطار شامل أو كحزمة معايير إلزامية؟ هذا هو موضع التعارض ويحتاج قراراً مستقلاً.
- **خطة تطبيق:** النطاق، الاستثناءات، المراحل، التوافق، القياس، الترحيل والرجوع. لا تستنتج هذه التفاصيل من اسم القرار.

### 2.3 بوابة القرار

| Decision item | المطلوب قبل الاعتماد | المالك/المراجع المطلوب | الحالة |
|---|---|---|---|

| ZT-166-02 | اختيار: إطار شامل ملزم، أو ضوابط محددة، أو توصية غير ملزمة | صاحب القرار + معماري النظام + C10 | PENDING DECISION |

## 3. تصادم معرفات COST

### 3.1 التصادم المصدرّي

المصدر 141–143 يستخدم COST-01..16 لاختبارات القبول، ويستخدم COST-01..12 لقرارات مقترحة. بالتالي فإن COST-01 إلى COST-12 ملتبسة دون تحديد نوع السجل.

### 3.2 Crosswalk مقترح لا يغير المصدر

| النطاق | المعرف الأصلي | الاسم المؤقت المقترح | ملاحظة |
|---|---|---|---|
| اختبارات القبول | COST-01..16 | COST-AT-01..16 | AT = Acceptance Test |
| قرارات التكلفة | COST-01..12 | COST-DEC-01..12 | DEC = Decision |

- يبقى المعرف الأصلي محفوظاً في source_alias/provenance.
- لا يعاد ترقيم أي اختبار أو قرار في السجلات الأصلية.
- لا تُحدّث مراجع الاختبارات أو الموافقات أو API قبل اعتماد namespace من مالك المواصفات.
- لا يعني هذا الاقتراح أن 16 اختباراً مفصلة أو منفذة؛ workpaper 137 يثبت أسماء/موضوعات الاختبارات ويذكر أن خطوات التنفيذ والبيانات والنتائج والأدلة تحتاج استكمالاً.

## 4. تصادم معرفات DASH

المصدر 141–143 يستخدم DASH-01..18 لاختبارات القبول وDASH-01..12 لقرارات مقترحة.

| النطاق | المعرف الأصلي | الاسم المؤقت المقترح | ملاحظة |
|---|---|---|---|
| اختبارات اللوحة | DASH-01..18 | DASH-AT-01..18 | اختبارات عرض وصلاحيات ومصدر بيانات وتحديث وRTL واستجابة |
| قرارات اللوحة | DASH-01..12 | DASH-DEC-01..12 | قرارات تصميم/حوكمة مقترحة |

يلزم الحفاظ على aliases وإثبات المصدر لكل معرف. لا تعتبر الشاشة أو قرار التصميم اختباراً، ولا تعتبر نتيجة العرض إثباتاً لملكية البيانات.

## 5. ملكية SH-11 والتكلفة والميزانية

### 5.1 الفصل المقترح للملكية

| الحقيقة/السجل | المالك المقترح في workpapers | حد الملكية |
|---|---|---|
| raw provider meter / usage evidence | المزود أو المجال المنتج | يحتفظ بالمصدر الأصلي |
| rate/rate card | المزود أو مالك العقد التجاري | مصدر السعر والعملة والتاريخ |
| normalized usage ledger | SH-11 | تطبيع الاستخدام مع source lineage وidempotency |
| cost calculation | SH-11 | يحفظ quantity/unit/rateRef/currency/rule version |
| estimate/forecast | SH-11 | يميز صراحة عن actual |
| budget definition | SH-11 تشغيلياً مع اعتماد صاحب الميزانية | الخدمة لا تعتمد ميزانية تجارية نيابة عن المالك |
| dashboard projection | C14 | قراءة فقط؛ source/version/as_of/freshness/ACL |
| budget settings | مالك إعداد المجال + SH-12 | C13 واجهة إدارة، لا مالك دلالة المفتاح |

هذه حدود مقترحة في الوثيقة 83 وليست اعتماداً نهائياً لمالك SH-11 أو أي سجل.

### 5.2 القرارات التي ما زالت مفتوحة

- تعيين مالك SH-11 التشغيلي وQualified OWN.
- اعتماد authoritative source لكل provider/meter/rate.
- اعتماد العملة ومصدر FX وتاريخه والدقة والتقريب.
- اعتماد الفصل بين estimate وmetered وinvoiced وreconciled وuncertain.
- اعتماد idempotency وإعادة الإرسال والتأخر والتسوية.
- تحديد صاحب اعتماد الميزانية وصلاحية تعديلها ونقلها والاستثناء.
- اعتماد التصنيف والاحتفاظ والوصول والتصدير.
- اعتماد schemas وإصدارات API/events والاختبارات.

### 5.3 عتبات الإنفاق

النسب 50% و75% و90% و100% في المصدر نسب ابتدائية مقترحة قابلة للتعديل، وليست حدوداً معتمدة أو ثوابت برمجية. لا يجوز تحويلها إلى إجراءات تلقائية.

قبل اعتماد أي عتبة يجب تحديد:
1. مالك الميزانية والنطاق والفترة والعملة.
2. هل العتبة تنبيه فقط أم تمنع التزاماً جديداً أم توقف مهمة أم تطلب موافقة.
3. كيفية التعامل مع التكاليف غير المؤكدة والفواتير المتأخرة والتسوية.
4. الاستثناءات وفصل طالب الاستثناء عن المعتمد.
5. ألا يؤدي إجراء التكلفة إلى تجاوز فحوص الأمن أو تعطيل اختبارات إلزامية.

## 6. الاستمرارية والتعافي: RTO/RPO/SLO/Freshness

### 6.1 تمييز المقاييس

| المصطلح | تعريفه في هذه المراجعة | ما لا يثبته |
|---|---|---|
| SLI | قياس فعلي بمصدر ووحدة ونافذة | لا يحدد هدفاً |
| SLO | هدف خدمة معتمد | لا يساوي SLA تلقائياً |
| SLA | التزام خارجي تعاقدي عند وجوده | لا يفترض من SLO |
| RTO | أقصى زمن استعادة معتمد لقدرة/خدمة | لا يستنتج من عبارة availability |
| RPO | أقصى فقد بيانات مقبول ومعتمد | لا يستنتج من تكرار النسخ |
| Freshness | حد تأخر معتمد لبيانات/إسقاط | لا يساوي وقت تشغيل الخدمة |
| Recovery drill cadence | تواتر اختبار التعافي | لا يثبت نجاح الاختبار |

### 6.2 مصفوفة اعتماد الأهداف

| النطاق | الهدف المطلوب | مصدر القياس/الاختبار | الحالة |
|---|---|---|---|
| الخدمات الحرجة | Availability SLI/SLO | SH-14 | OPEN / numeric TBD |
| مسارات API الحرجة | Latency/error-rate SLI/SLO | SH-14 + C07 | OPEN / numeric TBD |
| C14 projections | freshness per source | مصدر المجال + C14 | OPEN / numeric TBD |
| قواعد البيانات/فئات البيانات | RPO per class/service | Domain SoR + SH-15 | OPEN / numeric TBD |
| قدرات الأعمال | RTO per capability | مالك الأعمال + SH-15 | OPEN / numeric TBD |
| النسخ والاستعادة | verification/drill cadence | SH-15 + C07 | OPEN |
| failover/degraded mode | شروط fallback وfencing وعودة الكتابة | ملاك الخدمات + C10 | OPEN |
| recovery evidence | run/build/actor/time/source/checksums | SH-14/15 + C07 | OPEN |

لا تحدد هذه الوثيقة أرقاماً افتراضية؛ يجب أن تستند القيم إلى أثر الأعمال وتصنيف البيانات وقدرات المزود والقياس الفعلي والكلفة وموافقة المالك.

### 6.3 بوابة SH-15

لا يعلن التعافي مكتملاً لمجرد وجود backup record أو انتهاء restore job. يلزم:
- سلامة النسخة ومراجع التشفير وتوفر المفاتيح.
- consistency point معتمد لكل مصدر مشارك.
- موافقة الاستعادة المطلوبة وفصل الواجبات.
- تحقق العلاقات والعزل وسلامة البيانات بعد الاستعادة.
- تحقق freshness/health وإقرار مالكي الخدمات.
- evidence قابل للتتبع إلى نسخة وبيئة ووقت وفاعل.

جميع اختبارات BAK-87 الواردة في الحزمة تبقى SPECIFIED / NOT RUN ما لم يظهر دليل تنفيذ فعلي.

## 7. ارتباطات اعتماديات المراكز

الوثيقة 138 تستعيد ستة أنواع اعتماديات: INPUT وDECISION وSERVICE وVALIDATION وOPERATION وDELIVERY، و14 اختبار DEP-01..14، و10 قرارات DEP-DEC-01..10 مقترحة.

قواعد الإغلاق:
- لا تحول dependency edge إلى عقد معتمد دون owner وversion وconditions وvalidation.
- لا تساوي Satisfied مع Validated.
- لا تعتبر اختبارات DEP منفذة أو exact-linked لمجرد وجودها في workpaper.
- يجب ربط اعتماديات C11 للنشر بموافقات C10/C07 وSH-08/10/14/15 حسب العقد، دون إنشاء سلسلة تنفيذ تلقائية من المصفوفة وحدها.
- تبقى DEC-DEP-010 مقترحاً حتى موافقة صاحب القرار.

## 9. شروط الإغلاق قبل MPRTS

1. اعتماد أو رفض أو تأجيل قرار Zero Trust مع سجل موافقة ومبرر ونطاق.
2. اعتماد namespaces لـCOST وDASH مع aliases وتحديث cross-references دون محو المصدر.
3. تعيين مالك SH-11 وصاحب قرار كل ميزانية ومرجع بيانات التكلفة.
4. اعتماد عتبات الإنفاق والإجراءات أو تقرير صريح بأنها غير مطلوبة.
5. اعتماد RTO/RPO/SLO/freshness حسب الخدمة وفئة البيانات، أو توثيق نطاق مستثنى بموافقة.
6. تنفيذ اختبارات التكلفة واللوحة والتعافي والاعتماديات وتسجيل أدلتها.
7. ربط كل finding بمالك وقرار واختبار ودليل وإغلاق مستقل.
8. إصدار MPRTS candidate ثم اجتياز التدقيق النهائي وتوقيع المالكين.
9. طلب موافقة مستقلة وصريحة على بدء البرمجة بعد اعتماد المواصفات.

## 10. ما لا تسمح به هذه الوثيقة

- لا تعتمد Zero Trust أو تلغيه.
- لا تعتمد COST/DASH renaming أو عتبات الميزانية.
- لا تعين مالك SH-11 أو مالك الميزانية أو مالك KMS.
- لا تضع قيماً رقمية لـRTO/RPO/SLO أو freshness.
- لا تحول اختبارات SPECIFIED / NOT RUN إلى نتائج ناجحة.
- لا تنشئ APIs أو جداول أو خدمات أو صلاحيات.
- لا تمنح إذناً ببدء البرمجة.

**الخلاصة:** الوثيقة 166 تسجل بدقة نقاط القرار والاعتماد التي تمنع إغلاق الأمن والتكلفة واللوحة والتعافي، وتحدد الأدلة المطلوبة لكل منها. لم يتغير كود التطبيق أو API أو مخطط قاعدة البيانات. تبقى البرمجة متوقفة حتى اكتمال المواصفات واعتمادها، ثم موافقة المستخدم الصريحة المستقلة على بدء التنفيذ.
