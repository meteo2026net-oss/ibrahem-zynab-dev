## 2. سجل النتائج

### AUD-SEC-001 — مفتاح تشفير ثابت ومضمن في التطبيق

**الخطورة:** حرجة  
**الأدلة:** `app/src/main/java/com/example/data/security/CryptoUtils.kt`  
**الملاحظة:** قيمة مفتاح AES مشتقة من نص ثابت داخل مصدر التطبيق. كل نسخة تحتوي القيمة نفسها، ويمكن استخراجها من التطبيق المنشور أو من المصدر. هذا لا يحقق إدارة مفاتيح آمنة للأسرار طويلة الأجل.  
**الأثر:** من يحصل على بيانات التشفير ومصدر التطبيق يمكنه محاولة فك الأسرار المخزنة؛ لا ينبغي اعتبار الحقول المشفرة محمية من مالك نسخة التطبيق أو من تسرب المستودع.  
**المطلوب:** نقل التشفير إلى خدمة خلفية موثوقة مع إدارة مفاتيح منفصلة ودوران وإبطال، أو اعتماد تصميم مفاتيح جهاز/مستخدم مناسب للحالة. يلزم ترحيل الأسرار الموجودة وخطة تدوير قبل إزالة التصميم القديم.  
**الحالة:** مفتوح — لا تغيير للكود في هذه الجولة.

### AUD-SEC-002 — فشل التشفير يتحول إلى تخزين النص الأصلي

**الخطورة:** حرجة  
**الأدلة:** `CryptoUtils.encrypt` يعيد `plainText` عند وقوع استثناء.  
**الملاحظة:** سلوك fail-open؛ يمكن للمستودعات حفظ قيمة سرية كنص صريح إذا فشل التشفير دون إيقاف العملية أو إعلان فشلها.  
**المطلوب:** fail-closed: إيقاف الحفظ وإرجاع خطأ آمن، وعدم إعادة النص الأصلي مطلقاً، وإضافة اختبار يثبت عدم كتابة أي قيمة عند فشل التشفير.  
**الحالة:** مفتوح — يحتاج تعديل كود واختباراً.

### AUD-SEC-003 — فك الأسرار يجري في عميل Android رغم تسمية Backend Only

**الخطورة:** حرجة  
**الأدلة:** `SecretsVaultRepository.resolveSecretBackendOnly` في `app/src/main/java/com/example/data/repository/SecretsVaultRepository.kt` يستعلم Firestore ثم يستدعي `CryptoUtils.decrypt` داخل التطبيق.  
**الملاحظة:** اسم الوظيفة وتعليقها يوحيان بأن فك السر محصور بالخلفية، لكن التنفيذ داخل عملية Android. كما أن الوظيفة تستقبل اسم الخدمة والوكيل من المستدعي ولا تثبت هوية خدمة خلفية موثوقة.  
**المطلوب:** جعل حل المراجع عملية خلفية فقط، مع مصادقة خدمة إلى خدمة، وتفويض مركزي، وتدقيق محمي، وعدم إعادة النص الصريح إلى الواجهة أو سياق AI.  
**الحالة:** مفتوح.

### AUD-SEC-004 — فحص تفويض غير مكتمل داخل مسار حل الأسرار

**الخطورة:** عالية  
**الأدلة:** النموذج `VaultSecret` يحوي `allowedServices` و`allowedAgents` و`allowedOperations`; مسار الحل الظاهر يفحص `allowedServices` فقط، بينما يظهر `requestingAgent` في سجل التدقيق ولا يظهر فحص مقابلته بـ`allowedAgents` أو التحقق من العملية المطلوبة عبر `allowedOperations`.  
**الملاحظة:** لا يكفي وجود قوائم سماح في نموذج البيانات إذا لم تُطبق عند كل استخدام.  
**المطلوب:** عقد تفويض واضح يربط هوية الخدمة والوكيل والعملية والمشروع والسر، مع رفض افتراضي واختبارات سلبية لكل حد.  
**الحالة:** مفتوح.

### AUD-SEC-005 — قواعد Firestore تسمح بتعديل وحذف سجلات التدقيق من المالك

**الخطورة:** حرجة  
**الأدلة:** `firestore.rules`، مسار `audit_logs`.  
**الملاحظة:** القاعدة العامة تمنح المستخدم المالك صلاحية `update, delete`، بينما يقرر خط الأساس المعماري أن سجل التدقيق لا يجوز للمستخدم العادي أو الوكيل تعديله أو محو آثاره.  
**الأثر:** فقدان سلامة سجل التدقيق وإمكانية تغيير أدلة النشاط من العميل.  
**المطلوب:** جعل كتابة سجلات التدقيق عبر خدمة موثوقة فقط، ومنع التعديل والحذف الاعتياديين، مع آلية تصحيح append-only ومراقبة سلامة.  
**الحالة:** تعارض مباشر بين التنفيذ الحالي ومبدأ موثق؛ مفتوح.

### AUD-SEC-006 — قاعدة ملكية Firestore لا تثبت ثبات المالك بعد الإنشاء

**الخطورة:** عالية  
**الأدلة:** قواعد التحديث في `firestore.rules` تتحقق من `resource.data.userId == request.auth.uid`، ولا يظهر تحقق موازٍ من أن `request.resource.data.userId` بقي مساوياً للمستخدم نفسه.  
**الملاحظة:** قد يستطيع المالك الحالي تغيير حقل الملكية في السجل أثناء تحديثه. كما أن القواعد العامة لا تثبت عضوية المشروع أو المؤسسة أو تطابقها لكل سجل.  
**المطلوب:** منع تغيير حقول المالك والنطاق بعد الإنشاء إلا عبر تدفق نقل ملكية مصرح وموافق عليه، والتحقق من project/organization membership لكل عملية.  
**الحالة:** مفتوح.

### AUD-SEC-007 — بيانات الاعتماد والأسرار تخضع لقواعد قراءة عامة للمالك

**الخطورة:** عالية  
**الأدلة:** `firestore.rules` لمسارات مثل `project_secrets_vault` و`api_credentials` و`github_accounts` و`telegram_bots` و`google_accounts`.  
**الملاحظة:** قاعدة القراءة تسمح للمالك بقراءة المستند كاملاً، بما فيه حقول ciphertext/credentials metadata. وبالاقتران مع المفتاح الثابت المضمن في التطبيق، لا يوفر التشفير الحالي حد حماية موثوقاً.  
**المطلوب:** فصل metadata المرئية عن الأسرار، وإبقاء ciphertext ومراجع المفاتيح في مخزن خلفي محدود، وتحديد حقول القراءة المسموحة عبر تصميم البيانات/الخدمة بدلاً من الاعتماد على إخفاء الواجهة.  
**الحالة:** مفتوح.

### AUD-FUNC-001 — مجموعة ai_accounts مستخدمة في التطبيق وغير معرفة في قواعد Firestore

**الخطورة:** عالية  
**الأدلة:** `AiAccountsRepository.kt` ينفذ عمليات على `ai_accounts`، بينما لا يظهر مسار `match /ai_accounts/{...}` في `firestore.rules`.  
**الملاحظة:** قواعد Firestore ترفض الوصول افتراضياً للمسارات غير المطابقة؛ لذلك عمليات هذا المستودع مرشحة للفشل ما لم توجد قواعد أخرى خارج الملف المنشور أو إعدادات غير ظاهرة.  
**المطلوب:** تحديد ما إذا كانت المجموعة جزءاً معتمداً من التطبيق؛ ثم إضافة قواعد مخصصة متسقة مع نموذج الهوية والمشروع والأسرار، واختبارها عبر Firebase Emulator. لا تضف قاعدة عامة مفتوحة كحل سريع.  
**الحالة:** خلل توافق ظاهر بين الكود والقواعد؛ يحتاج تحققاً تنفيذياً.

### AUD-FUNC-002 — عمليات GitHub في التطبيق تتضمن محاكاة لا اتصالاً حقيقياً

**الخطورة:** عالية وظيفياً  
**الأدلة:** `IntegrationsRepository.kt`، الدوال `getSampleRepositoriesForAccount` و`createCommit` و`createPullRequest`.  
**الملاحظة:** بيانات المستودعات أمثلة ثابتة، ومعرف commit ورقم PR مولدان محلياً؛ لا يظهر في هذه الدوال استدعاء GitHub API لإنشاء commit أو pull request فعلي.  
**المطلوب:** وسم الواجهات بأنها Demo/Simulated إلى أن ينفذ تكامل فعلي، أو استكمال OAuth/صلاحيات GitHub/API مع اختبارات عقدية. يمنع عرض نتيجة محاكاة على أنها عملية تمت على GitHub.  
**الحالة:** مفتوح.

### AUD-FUNC-003 — تدفق حسابات AI يتضمن بيانات رمزية مولدة محلياً

**الخطورة:** عالية وظيفياً  
**الأدلة:** `AiAccountsRepository.kt` ينشئ قيمة `oauth_tok_` عشوائية عند مسار ربط الحساب، بدلاً من إظهار تبادل OAuth حقيقي في الكود المفحوص.  
**الملاحظة:** لا يجوز اعتبار الحساب متصلاً بمزود خارجي اعتماداً على token شكلي أو سجل نجاح محلي.  
**المطلوب:** تنفيذ OAuth حقيقي مع state/PKCE والتحقق من issuer/audience/expiry وتخزين آمن، أو توضيح أن المسار تجريبي.  
**الحالة:** مفتوح.

### AUD-FUNC-004 — تدفق Telegram يتضمن محاكاة ووجهة webhook غير مثبتة

**الخطورة:** عالية وظيفياً  
**الأدلة:** `IntegrationsRepository.kt`، `simulateIncomingTelegramEvent`، وقيمة webhook URL ضمن النطاق `api.metra-ai.control`.  
**الملاحظة:** الدالة تسجل حدثاً تجريبياً محلياً؛ لم يظهر في الملف المفحوص ما يثبت استقبال webhook فعلياً أو التحقق من توقيع/سر Telegram. كما أن صلاحية النطاق وإعداده لم يتم التحقق منهما.  
**المطلوب:** الفصل الواضح بين المحاكاة والإنتاج، والتحقق من ملكية النطاق ونقطة webhook، والتحقق من سر webhook/هوية الطلب، ومنع قبول أحداث غير موثوقة.  
**الحالة:** مفتوح.

### AUD-BUILD-001 — ملفات Gradle Wrapper غير مكتملة في المستودع

**الخطورة:** عالية لقابلية البناء  
**الأدلة:** شجرة المستودع تحتوي `gradle/wrapper/gradle-wrapper.properties` فقط؛ لم تظهر `gradlew` أو `gradlew.bat` أو `gradle-wrapper.jar`.  
**الملاحظة:** لا يمكن تشغيل البناء بالطريقة القياسية عبر Gradle Wrapper من نسخة المستودع الحالية.  
**المطلوب:** استعادة ملفات Wrapper الرسمية المتوافقة مع Gradle 9.3.1 والتحقق من checksums، أو توثيق بديل بناء معتمد. لا تُنشأ ملفات wrapper يدوياً أو من مصدر غير موثوق.  
**الحالة:** نقص ملفي/تشغيلي ظاهر.

### AUD-BUILD-002 — لا يوجد CI workflow ظاهر في المستودع

**الخطورة:** متوسطة  
**الأدلة:** الاستعلام عن `.github/workflows` أعاد 404، ولم يظهر مجلد workflow في شجرة الملفات.  
**الملاحظة:** لا توجد أدلة في المستودع على تشغيل build/lint/unit tests تلقائياً عند كل تغيير.  
**المطلوب:** بعد اعتماد استراتيجية CI، إضافة workflow محدود الصلاحيات يشغل فحص الوثائق والاختبارات والبناء، دون كشف أسرار أو تنفيذ نشر تلقائي.  
**الحالة:** غير موجود في الشجرة المفحوصة.

### AUD-TEST-001 — لا يوجد دليل على تنفيذ الاختبارات

**الخطورة:** عالية للثقة بالإصدار  
**الأدلة:** ملفات اختبارات وحدة واختبار Android موجودة، لكن لم يُشغّل Gradle أو Emulator في هذه الجولة.  
**الملاحظة:** لا يمكن وصف المشروع بأنه يبني أو أن الاختبارات ناجحة. لا تظهر في هذه الجولة نتائج CI أو تقارير test artifacts.  
**المطلوب:** بعد إصلاح قابلية البناء، تشغيل unit tests وlint وAndroid instrumentation وFirebase Rules Emulator tests، وحفظ تقارير فعلية مرتبطة بالـcommit.  
**الحالة:** غير متحقق تنفيذياً.

### AUD-CONFIG-001 — سياسة النسخ الاحتياطي في Android تحتاج مراجعة أسرار

**الخطورة:** عالية  
**الأدلة:** `AndroidManifest.xml` يحدد `allowBackup=true`، وملفا `backup_rules.xml` و`data_extraction_rules.xml` لا يحددان استثناءات بيانات واضحة (TODO/نماذج افتراضية).  
**الملاحظة:** لم يتم إثبات أن بيانات حساسة محلية تُنسخ حالياً، لكن الإعداد لا يقدم سياسة صريحة لاستبعاد الأسرار والرموز والبيانات الحساسة.  
**المطلوب:** جرد التخزين المحلي أولاً، ثم تحديد ما يسمح بنسخه وما يمنع، واختبار cloud backup وdevice transfer على إصدارات Android المدعومة.  
**الحالة:** مراجعة مطلوبة قبل الإنتاج.

### AUD-DOC-001 — تقرير التدقيق السابق يحتوي وصفاً قديماً للجذر

**الخطورة:** منخفضة توثيقياً  
**الأدلة:** `docs/specifications/00-repository-audit.md` يقول إن README الجذري لم يكن موجوداً، بينما README موجود في اللقطة الحالية.  
**الملاحظة:** التقرير يحتاج تمييزاً زمنياً بين لقطة الفحص السابقة والحالة الراهنة.  
**المطلوب:** تحديث صياغة التقرير لتوضيح أن الملاحظة تاريخية وأن README موجود حالياً، مع إبقاء سجل التغيير.  
**الحالة:** سيعالج ضمن تحديث هذه الجولة.

## 3. الترتيب المقترح للإصلاح

1. **أولوية فورية:** AUD-SEC-001 إلى AUD-SEC-007، خصوصاً وقف أي اعتبار للتشفير الحالي حماية إنتاجية للأسرار.
2. **أولوية عالية:** AUD-FUNC-001 ومطابقة جميع مجموعات Firestore مع عمليات التطبيق.

4. **أولوية بناء:** AUD-BUILD-001 ثم إعداد CI بعد تحديد سياسة البناء.

6. **أولوية إنتاج:** AUD-CONFIG-001 ومراجعة النسخ الاحتياطي.

## 4. حدود هذه الجولة

- لم تتغير ملفات Kotlin أو Gradle أو Firebase أو Firestore.
- لم يتم نشر قواعد Firestore أو تغيير إعدادات Firebase.
- لم يتم تشغيل build أو test أو emulator أو penetration test.
- لا تشمل النتائج تدقيقاً لكل endpoint خارجي أو كل سيناريو runtime.
- لا تعني هذه القائمة أنها جميع أخطاء المشروع؛ إنها جميع النتائج التي أمكن إثباتها من نطاق الفحص الحالي، وتحتاج جولات أعمق.

## 5. بوابة الإصلاح

تُعالج العيوب البرمجية بعد موافقة منفصلة على بدء مرحلة إصلاح التطبيق. عندها يجب أن يكون كل إصلاح في commit واضح، مسبوقاً بمراجعة أثر وخطة رجوع واختبار، ثم يعاد فحص الملفات والنتائج بعد الرفع.

**الخلاصة:** توجد مخاطر أمنية ووظيفية حقيقية في التطبيق الحالي، ولا يصح اعتباره جاهزاً للإنتاج اعتماداً على هذه اللقطة. الأولوية هي حماية الأسرار وسلامة سجل التدقيق وقواعد العزل، ثم إثبات قابلية البناء والاختبارات، مع عدم خلط ذلك باعتماد مواصفات المنتج المستهدف.
