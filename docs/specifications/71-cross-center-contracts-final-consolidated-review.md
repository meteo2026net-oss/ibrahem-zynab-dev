**الحالة:** CONSOLIDATED-REVIEW-CANDIDATE / DERIVED-DRAFTS / NOT-APPROVED / NO-IMPLEMENTATION  
**التاريخ:** 2026-11-15  
**النطاق:** توحيد عقود 59–70 مع المصادر 19–27 و32 و36 و45–50 و56–57.  
**الغرض:** بيان ملكية البيانات والواجهات والصلاحيات والاختبارات والتبعيات ومنع تضارب المسؤوليات. هذه مراجعة وثائقية، لا اعتماد نهائي ولا ERD/API منشور ولا نتيجة اختبار.

## 1. النتيجة التنفيذية

اكتملت مسودات عقود المراكز الأربعة عشر على مستوى أولي:
- C01–C07: الوثائق 59–63.
- C08–C14: الوثائق 64–70.

الوثائق 64–70 تسد فجوة صياغة العقود للمراكز المتبقية، والوثيقة 71 تجمع الحدود والتبعيات ومخاطر التداخل. جميع التفاصيل الهندسية المستحدثة في 59–71 موسومة مسودة/مقترح وتحتاج مراجعة مالك المركز والخدمات المشتركة. لا يعني ذلك أن كل متطلب أو حقل أو شاشة أصبح مكتملاً.

## 2. قاعدة ملكية البيانات الموحدة

تعتمد المراجعة قاعدة من ثلاث طبقات:

1. **مالك حقيقة المجال (System of Record):** المركز الذي يملك معنى البيانات وقرارها وإصداراتها، ويكون وحده جهة الكتابة الدلالية عبر عقده.
2. **مالك الخدمة المشتركة:** الخدمة التي تملك بيانات تشغيل القدرة المشتركة فقط (جلسات، موافقات، تدقيق، مهام، تسليم أحداث، تخزين، فهرسة، إعدادات مشتركة، موصلات، telemetry، backup metadata).
3. **المستهلك/العرض/الإسقاط:** يقرأ عبر API مصرح، ويمكنه تخزين projection/cache مع provenance وfreshness، لكنه لا يصبح مالك المصدر.

## 4. واجهات الاتصال الموحدة

### 4.1 غلاف الطلب المقترح

كل أمر/استعلام بين المراكز يحمل، عند انطباقه:
- requestId وcorrelationId وidempotencyKey للعمليات القابلة للإعادة.
- actorRef وorganizationRef وworkspaceRef وprojectRef بحسب النطاق.
- resourceRef وexpectedVersion في عمليات التعديل.
- contractName وcontractVersion.
- purpose/consent context عند معالجة البيانات الشخصية أو الحساسة.
- trace context وdeadline/timeout.
- مصدر التفويض policy decision reference، لا دور مرسل من الواجهة فقط.

هذه بنية مشتقة تحتاج مطابقة واعتماداً مع الوثيقتين 25 و27؛ لا تعتبر schema نهائياً.

### 4.2 أنواع التفاعل

- Query: قراءة scoped، دون side effects.
- Command: طلب تغيير يمر عبر مالك المجال.
- Event: إشعار حقيقة حدثت، لا أمر خفي.
- Approval: قرار بشري/مفوض عبر SH-03.
- Internal task: عمل غير متزامن عبر SH-08 مع status ومحاولات وإلغاء.

### 4.3 قواعد التوافق

- لا يكتب مركز في مخزن مركز آخر مباشرة.
- لا يستدعي consumer API مالكاً مع تجاوز التفويض أو النسخة.
- versioning للعقود مع سياسة deprecation.
- أخطاء موحدة دون تسريب أسرار أو بيانات خارج النطاق.
- timeout/retry/backoff/circuit breaker بحسب idempotency ونوع العملية.
- event schema versioning وdeduplication وdead-letter.
- عدم تحويل event delivery إلى source of truth.
- الموافقة ترتبط ببصمة/نسخة المورد؛ أي تغيير يبطل الموافقة القديمة عند انطباق السياسة.

## 6. الصلاحيات والموافقات

المبدأ المقترح:
1. SH-01 يثبت الهوية والجلسة.
2. SH-02 يقيّم السماح على actor/action/resource/tenant/project/context.
3. مالك المجال يتحقق من حالة المورد وقواعد العمل والنسخة.
4. SH-03 يدير الموافقات عندما تتطلب السياسة قراراً منفصلاً.
5. SH-04 يسجل الحدث والقرار بصورة لا يستطيع الوكيل أو المركز المستهلك تعديلها.
6. الوكيل لا يملك صلاحية ضمنية؛ كل أداة ونطاق وزمن ومورد يحتاج تفويضاً صريحاً.
7. الموافقات لا تنشأ من مجرد إخفاء زر/إظهاره؛ التحقق خادمي.
8. عند فشل خدمة التفويض أو غياب السياق: رفض آمن.

مصفوفة الأدوار النهائية غير متوفرة بعد؛ أدوار «مالك/مدير/محرر/مراجع/قارئ/مدقق/وكيل» أوصاف أولية فقط حتى اعتماد RBAC/ABAC من المالكين.

### تصنيف حالة الاختبارات

- **TEST-SPECIFIED:** وصف حالة اختبار في وثيقة.
- **TEST-IMPLEMENTED:** حالة اختبار موجودة في كود/بيئة قابلة للتشغيل.
- **TEST-EXECUTED:** تشغيل موثق ببيئة ونسخة ووقت.
- **TEST-PASSED/FAILED:** نتيجة مرتبطة بسجل تشغيل وartifact.
- لا يجوز ترقية حالة إلى مرحلة أعلى بلا evidence_ref وcommit/build/test-run محدد.

لا تتضمن هذه المراجعة أي ادعاء بأن اختبارات المراكز الجديدة أو القديمة نُفذت.

## 10. أثر هذه الدفعة على تتبع المحاور

أضيفت مسودات C08–C14 للرجوع إليها عند تحديث تتبع المحاور التي تتقاطع معها، لكن لا تُرقى أي خانة DATA/API/AUTH/TEST إلى APPROVED أو EXECUTED. يجب أن تبقى حالات المصدر/المسودة/المراجعة كما هي حتى تتم مراجعة مالك كل محور وتحديد المطابقة الدقيقة. لا تعيد هذه الوثيقة احتساب المحاور أو تغلق GAP-044.

## 11. الخلاصة

أصبح لدينا تسلسل وثائقي متصل لعقود المراكز C01–C14 ومراجعة موحدة لحدود الملكية والتبعيات والواجهات والاختبارات. لكنه **مرشح مراجعة نهائية** لا مواصفات معتمدة. لم تتغير الشفرة، ولم تنفذ اختبارات منتج، ولم يصدر إذن بدء البرمجة.


## 10. نتائج تدقيق الاتساق التفصيلي وحدود الملكية

أضيف السجل 72 لتحديد عشر نقاط تداخل محددة OWN-01..OWN-10، خاصة C08/SH-06 وC09/SH-13 وC10/SH-01..04 وC12/SH-07/16 وC13/SH-12 وC11/SH-08/10/14/15 وC04/مراكز المجال وC07/SH-14 وC14/المصادر وC06/حوكمة الوكلاء. يوصي السجل بفصل حقيقة المجال عن metadata التشغيلية والخدمات المشتركة. هذه ليست قرارات معتمدة؛ لا تعدل الوثيقة 36 قبل موافقة المالكين. راجع الوثيقة 72 لمصفوفة RACI وبوابة العقود وترتيب الاعتماد ومعايير الاختبارات. جميع الاختبارات لا تزال مقترحة وغير منفذة.

## 11. مطابقة مستوى الكيان والحقل

أضيفت الوثيقة 73 لمطابقة كيانات C01–C14 وحقولها الموصوفة مع ملكية الخدمات SH-01..SH-16. حددت 26 مسألة FLD-01..26، تشمل اختلاف organization_id/tenant_id، ازدواج سجل الصفحات، ازدواج AI tasks مع SH-08، asset/version وgrants مع SH-06/SH-02، policy decisions/audit events مع SH-02/SH-04، content/index مع SH-16/SH-07، settings مع SH-12، وprojection schema في C14. هذه نتائج تدقيق وتوصيات وليست قرارات معتمدة. لا تعدل مصفوفة 36 قبل توقيع المالكين. لا توجد schemas تنفيذية أو اختبارات منفذة.
