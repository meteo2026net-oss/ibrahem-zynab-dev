# 24 — ملكية البيانات والنموذج المنطقي الموحد

**الحالة:** RECOVERED_DETAILED / PENDING SCHEMA REVIEW  
**المصدر:** الفصل 134 من ملف التصدير 2026-11-10-export-part-04.txt.  
**حدود المصدر:** أسماء مجموعات الكيانات وبعض الجداول والحقول والقواعد مستعادة؛ كثير من الجداول «مقترح» في المصدر وليست مخططاً معتمداً أو SQL منفذاً. لا تحول أسماء الجداول إلى قرار تقني نهائي دون مراجعة.

## 1. أهداف النموذج

الفصل 134 يحدد نموذجاً منطقياً يهدف إلى منع تكرار الكيانات، وتحديد مالك كل كيان، ودعم المؤسسات والمستخدمين والمشاريع والبيئات، وربط المتطلبات بالتصميم والكود والاختبارات والوثائق، وحفظ التاريخ والإصدارات، ودعم الموافقات والتدقيق والمهام والأحداث والملفات والتكاملات والنسخ الاحتياطي، ومنع الوصول بين المؤسسات والمشاريع.

يقسم البيانات إلى سبع مجموعات منطقية:
1. البيانات الأساسية.
2. بيانات المراكز.
3. البيانات المشتركة.
4. البيانات التشغيلية.
5. الأمن والحوكمة.
6. المعرفة والوثائق.
7. بيانات المنصة وإعداداتها.

هذا تقسيم منطقي، ولا يفرض سبع قواعد بيانات مستقلة.

## 2. الكيانات الأساسية المستعادة

| الكيان/الجدول المقترح | المالك المنطقي | حقول/خصائص مستعادة | قواعد المصدر |
|---|---|---|---|
| organizations | منصة/نطاق المؤسسة | id، name، slug، status، plan_id، settings_id، created_at، updated_at | حالات مقترحة Active/Suspended/Pending/Archived؛ plan_id مشروط باعتماد الاشتراكات |
| users | خدمة الهوية للهوية وملف المستخدم العام | id، display_name، email_reference، avatar_asset_id، locale، timezone، account_status، timestamps | لا كلمات مرور أو أسرار مصادقة في هذا الجدول |
| organization_memberships | الهوية/العضويات | id، organization_id، user_id، membership_status، joined_at، invited_by، default_role_id | قيد UNIQUE(organization_id,user_id) |
| workspaces | المؤسسة/مساحة العمل | id، organization_id، name، description، workspace_type، status، created_by، created_at | المؤسسة تمتلك مساحات العمل |
| projects | إدارة المشاريع C01 | id، organization_id، workspace_id، name، slug، description، project_type، lifecycle_status، default_environment_id، created_by، timestamps، archived_at | المشروع يتبع مؤسسة واحدة ومساحة عمل؛ كل سجل مشروع يجب أن يحمل نطاق المؤسسة والمشروع أو يرتبط بهما بعلاقة موثوقة |

**قواعد العلاقات:**
- المؤسسة تمتلك مساحات العمل.
- مساحة العمل تحتوي مشاريع.
- المشروع تابع لمؤسسة واحدة.
- المستخدم قد ينضم إلى مؤسسات متعددة.
- المستخدم قد يشارك في مشاريع متعددة.
- المشروع قد يمتلك بيئات متعددة.
- عضوية المؤسسة لا تعني تلقائياً صلاحية كاملة على كل المشاريع.

## 3. ملكية بيانات المراكز الأربعة عشر

| المركز | البيانات المملوكة وفق الفصل 134.5 | حدود مهمة |
|---|---|---|
| C01 إنشاء المشروع | المتطلبات، الشخصيات، الأدوار، التحليل، الافتراضات | C01 يملك المتطلبات؛ لا يملك بيانات التصميم أو الكود |
| C02 التصميم | مستندات التصميم، العناصر، الطبقات، المكونات، التفاعلات | يملك design documents وإصداراتها |
| C03 الصفحات والتنقل | الصفحات، المسارات، القوائم، الانتقالات، الرحلات | لا يغير صلاحيات الخلفية من تلقاء نفسه |
| C04 البيانات | المصادر، الجداول، العلاقات، القيود، الاستعلامات، الترحيلات | يملك schema/data contracts؛ لا يملك سجلات الهوية العامة |
| C05 البرمجة | الملفات البرمجية، المعمارية، الاعتماديات، APIs، مخرجات التوليد | لا يملك اعتماد الكود أو نتائج الجودة |
| C06 فريق AI | الوكلاء، المهارات، المهام الذكية، الذاكرة، التقييمات | لا يملك صلاحيات مطلقة أو ذاكرة مشاريع أخرى |
| C07 الجودة | خطط الاختبار، الحالات، النتائج، العيوب، بوابات الجودة | لا يملك سياسات الأمن أو قرار النشر |
| C08 الملفات والوسائط | الأصول، المرفقات، التصنيفات، الإصدارات، التخزين | يملك asset records؛ لا يملك مضمون الوثائق أو التصميم |
| C09 التكاملات | الاتصالات، المحولات، تعريفات الخدمات، اختبارات التكامل | يملك connector configs/contracts وليس بيانات المصدر الخارجية |
| C10 الأمن والحوكمة | الهوية، الصلاحيات، السياسات، التدقيق، الحوادث | الفصل يضع الهوية والصلاحيات هنا؛ ينسق ذلك مع SH-01/02 ولا يعني تكرار مخازن الهوية |
| C11 البناء والنشر | ملفات البناء، خطوط CI/CD، الإصدارات المنشورة، عمليات النشر | يملك build/deployment records؛ لا يملك الكود المصدر |
| C12 المعرفة والتوثيق | الوثائق، القرارات، المراجع، المعرفة والفهرسة | يملك توثيق المعرفة وروابط المصادر؛ لا يصبح مالك المتطلبات أو الكود الأصلي |
| C13 الإعدادات | إعدادات المنصة والمشروع والمستخدم | يخزن القيم وفق النطاق؛ الأسرار خارج settings values |
| C14 لوحة التحكم | مؤشرات العرض والتجميعات ولوحات المتابعة | قراءة وتجميع فقط؛ لا تصبح مصدر الحقيقة لبيانات المراكز |

**ملاحظة مطابقة:** توجد تداخلات لفظية بين «الهوية» في C10 وSH-01 Identity Service. التفسير المتسق: C10 يملك سياسات الأمن والحوكمة ومجال إدارة الضوابط، بينما SH-01 يقدم قدرة المصادقة المشتركة، وSH-02 يقدم التفويض. يجب اعتماد مصفوفة دقيقة للملكية قبل تصميم الجداول.

## 4. نموذج تتبع المتطلبات

الكيانات المقترحة في الفصل 134.6:
- project_requirements
- requirement_versions
- requirement_relationships
- requirement_artifact_links
- requirement_acceptance_criteria

القواعد:
- معرف موحد للمتطلب.
- لا يحذف المتطلب إذا ارتبط بمخرجات معتمدة.
- التغيير ينشئ إصداراً جديداً.
- يجب معرفة العناصر المتأثرة بالتغيير.
- كشف المخرجات التي لا ترتبط بمتطلب أو قرار أو مهمة مبررة.
- كل نتيجة اختبار قابلة للتتبع إلى المتطلب الذي تتحقق منه.

مسار التتبع المقترح:
Requirement → Design → Navigation → Data Contract → Code → Test → Security Policy → Knowledge Document → Release Evidence.

## 5. نموذج الإصدارات ولقطة المشروع

الكيانات المقترحة في الفصل 134.7:
- versioned_resources
- resource_versions
- version_relationships
- change_sets
- change_set_items
- version_approvals
- version_tags
- version_comparisons
- project_snapshots

لقطة المشروع تجمع مراجع إصدارات متسقة للمتطلبات والتصميم والتنقل والبيانات والكود والاعتماديات وخطة الاختبار والسياسات وإعدادات البناء. الهدف إعادة بناء الحالة التي أنتجت artifact دون نسخ كل المحتوى إلى سجل ضخم.

**قاعدة:** قرار اعتماد إصدار يجب أن يشير إلى resource version/fingerprint محدد؛ اعتماد نسخة لا يعتمد النسخة التالية تلقائياً.

## 6. نماذج البيانات المشتركة المستعادة

### 6.1 الموافقات — 134.8
الجداول المقترحة: approval_requests، approval_steps، approval_decisions، approval_assignments، approval_evidence، approval_policies، approval_delegations، approval_events.

حقول الطلب: id، organization_id، project_id، requested_by، domain، resource_type، resource_id، resource_version، action_type، impact_level، risk_summary، estimated_cost، status، created_at، expires_at.

الحالات: Draft، Submitted، Pending، Approved، Rejected، Changes Requested، Expired، Cancelled، Superseded.

### 6.2 المهام والأحداث — 134.9
الجداول المقترحة: tasks، task_attempts، task_dependencies، task_assignments، task_progress_events، task_outputs، task_errors، task_cancellation_requests، event_outbox، event_inbox، event_subscriptions، event_delivery_attempts.

قواعد: فصل المهمة عن محاولاتها؛ حفظ نتائج متعددة؛ استخدام Outbox/Inbox عند الحاجة لمنع فقد الأحداث وتكرار الآثار.

### 6.3 الملفات والأصول — 134.10
الجداول المقترحة: assets، asset_versions، asset_storage_objects، asset_links، asset_permissions، asset_metadata، asset_processing_jobs، asset_checksums، asset_licenses، asset_retention_records.

قواعد: الفصل بين الملف الفعلي وسجل الأصل وروابطه وصلاحياته وإصداراته؛ مشاركة الأصل نفسه عند الملاءمة دون نسخ غير ضروري؛ لا حذف آمن دون مراجعة الارتباطات.

### 6.4 الذكاء الاصطناعي — 134.11
الجداول المقترحة: ai_agents، ai_agent_versions، ai_skills، ai_agent_skills، ai_tools، ai_agent_tools، ai_agent_permissions، ai_workflows، ai_workflow_runs، ai_memory_spaces، ai_memory_items، ai_memory_sources، ai_model_providers، ai_models، ai_usage_records، ai_evaluation_runs.

نطاقات الذاكرة: منصة معتمدة، مؤسسة، مشروع، مهمة، جلسة. لا تنتقل ذاكرة مشروع إلى مشروع آخر تلقائياً. يجب حفظ المصدر والثقة والتاريخ والاحتفاظ.

### 6.5 الإعدادات — 134.12
النطاقات: Platform، Organization، Workspace، Project، Center، User، Environment، Integration.

الجداول المقترحة: settings_definitions، settings_values، settings_schemas، settings_versions، settings_overrides، settings_change_history.

قاعدة: ترتيب الوراثة صريح، وبعض السياسات الأمنية لا يمكن للمستويات الأدنى إضعافها. لا تخزن الأسرار نصاً صريحاً؛ تستخدم secret references.

### 6.6 الهوية والصلاحيات — 134.13
الجداول المقترحة: identities، identity_providers، organization_memberships، workspace_memberships، project_memberships، roles، permissions، role_permissions، access_policies، policy_rules، permission_grants، temporary_grants، access_decisions، security_audit_logs.

أنماط التفويض: RBAC، ABAC، Resource-Level Access، Environment-Level Access.

### 6.7 التدقيق — 134.14
الجداول المقترحة: audit_events، audit_event_sources، audit_integrity_checkpoints، audit_export_jobs، audit_retention_policies.

يسجل الفاعل ونوع هويته والنطاق والعملية والمورد والإصدار السابق والجديد والوقت والخدمة والنتيجة والموافقة والمهمة المرتبطة. يمنع التعديل والحذف الاعتيادي، ويقيد الاطلاع والتصدير، ولا يسجل الأسرار.

## 7. قواعد تصميم البيانات المستعادة

- استخدام UUID أو معرفات قوية؛ لا تستخدم اسم المورد كمفتاح أساسي.
- عدم تغيير معرف المورد عند إعادة تسميته.
- استخدام قيود مفاتيح خارجية حقيقية حيث يلزم.
- منع العلاقات العابرة للمؤسسات.
- تعريف قيود uniqueness ضمن النطاق الصحيح.
- تحديد nullable/default/check constraints.
- فهرسة مفاتيح النطاق والبحث والارتباطات.
- تعريف حذف منطقي أو فعلي وسياسة retention بحسب نوع البيانات.
- استخدام إصدارات schema وترحيلات قابلة للمراجعة.
- فصل operational data عن audit data.
- عدم جعل cache مصدراً للحقيقة.
- عدم تخزين أسرار في جداول الإعدادات العادية.

## 8. قاموس البيانات الإلزامي

لكل جدول يجب توثيق:
اسم الجدول، الوصف، المركز المالك، مستوى الملكية، الحقول وأنواعها، required/optional، defaults، القيود، PK/FK، الفهارس، سياسات الوصول، تصنيف الحساسية، الاحتفاظ، العلاقات، المصدر، المستهلكون، قواعد الترحيل، واختبارات سلامة البيانات.

مثال مصدر: project_requirements مملوك لـC01، يعزل على المؤسسة والمشروع، له UUID وحالة وإصدارات وتدقيق، والحذف مقيد، ويستهلكه التصميم والبرمجة والاختبارات والمعرفة.

## 9. اختبارات قبول الفصل 134

المعرفات المستعادة DATA-01..DATA-18:
- DATA-01 إنشاء مؤسسة.
- DATA-02 عضوية مستخدم في مؤسستين.
- DATA-03 إنشاء مشروع وربطه بالمؤسسة ومساحة العمل.
- DATA-04 رفض سجل دون مالك صحيح.
- DATA-05 رفض علاقة بين مؤسستين.
- DATA-06 إصدار جديد عند تحديث متطلب معتمد.
- DATA-07 عدم اعتماد النسخة القديمة تلقائياً.
- DATA-08 ربط متطلب بتصميم وكود.
- DATA-09 منع تكرار آثار معالجة الحدث.
- DATA-10 حفظ تاريخ محاولات المهمة.
- DATA-11 منع إتلاف أصل مستخدم.
- DATA-12 استعادة العلاقات والإصدارات للمشروع.
- DATA-13 خطة ترحيل موثقة.
- DATA-14 رفض الوصول لذاكرة مشروع آخر.
- DATA-15 احترام صلاحيات المورد في البحث.
- DATA-16 التحقق من سلامة سجل التدقيق.
- DATA-17 استعادة نسخة احتياطية واتساقها.
- DATA-18 ترحيل دون فقد العلاقات أو الإصدارات.

هذه حالات قبول موثقة في المصدر، وليست نتائج تنفيذ.

## 11. الفجوات المتبقية

1. تحويل الأسماء المقترحة إلى ERD موحد ومراجعته.
2. استكمال الحقول والأنواع والقيود لجميع كيانات المراكز.
3. اعتماد owner/service لكل كيان دون تداخل C10 وSH-01/02.
4. اعتماد نموذج عزل tenant على مستوى كل مخزن.
5. ربط الكيانات بعقود API/events في الفصل 135.
6. اعتماد retention/deletion حسب فئات البيانات والولاية القانونية.
7. تحديد استراتيجية migrations وcompatibility.
8. ربط كل اختبار DATA-01..18 بخطة تنفيذ وبيئة ودليل.
9. مطابقة أسماء الجداول مع قرارات الخط التقني النهائي.

**الخلاصة:** الفصل 134 مستعاد بتفصيل جيد، وأصبح له سجل ملكية ونموذج منطقي قابل للمراجعة. لكنه ليس schema نهائياً ولا إذناً بإنشاء قاعدة البيانات.
