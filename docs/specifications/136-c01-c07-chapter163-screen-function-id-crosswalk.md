## 2. مطابقة كتالوجات الشاشات

### C01–C04
- ملف 02 يسجل الأعداد نفسها: C01=12، C02=15، C03=14، C04=17، لكنه يعرض أسماء الشاشات في قائمة وصفية دون استخدام معرفات Snn في النص المسترجع.
- ملف 19 يصرح أن صيغة Cxx-SCR-yy معرف توثيقي مقترح، وأن تفاصيل المدخلات والمخرجات والصلاحيات والاختبارات مشتقة وليست مصدراً أصلياً.
- لذلك لا يجوز مساواة C01-S01 مع C01-SCR-01 آلياً حتى لو بدا الترتيب متطابقاً؛ يلزم crosswalk موثق لكل شاشة ومراجعة مالك المركز.
- لا تظهر في ملف 19 معرفات Fnn المصدرية للمراكز C01–C04؛ وهو كتالوج تشغيلي مشتق وليس استعادة لمعرفات وظائف الفصل 163.

### C05–C07
- ملف 12 يحفظ الوظائف المصدرية المرقمة C05-F01..16 وC06-F01..18 وC07-F01..18، والأعداد تطابق الفصل 163.
- ملف 20 يوسع الوظائف الـ52 إلى عقود تشغيلية مشتقة، ويصرح بأنه لا يدعي استعادة نصوص الفصول الأصلية ولا اعتماد API أو schema أو نتيجة اختبار.
- يجب الحفاظ على IDs الأصلية في 12، وإبقاء تفاصيل 20 في حالة DERIVED DRAFT إلى أن تعتمد من المالك.
- عدد شاشات C05–C07 في 02 يطابق 16/18/19، لكن أقسام B-01–B-07 تسرد معرفات الشاشة؛ يجب حفظها في سجل الشاشات إذا لم تكن محفوظة في مصدر آخر.

## 3. مواضع الاختلاف التي يجب ألا تُمحى

1. **صيغة معرف الشاشة:** المصدر يستخدم Cxx-Snn؛ ملف 19 يستخدم Cxx-SCR-yy بوصفه معرفاً مقترحاً. يجب إنشاء جدول aliases/identity crosswalk، لا استبدال أحد المعرفين بالآخر.
2. **معرفات الوظائف C01–C04:** الفصل 163 يتضمن C01-F01..12 وC02-F01..15 وC03-F01..14 وC04-F01..16. الكتالوج 19 لا يقدم هذه المعرفات الأصلية؛ يجب استعادتها إلى سجل مستقل وربطها بأوصاف الوظائف بعد المطابقة.
3. **C05–C07:** المعرفات والأعداد محفوظة في 12، بينما 20 طبقة تفصيل مشتقة؛ لا تخلط المصدر بالاشتقاق.
4. **اختبارات القبول:** الفصل 163 يسرد معرفات C01-AT-01..15 وC02-AT-01..15 وC03-AT-01..18 وC04-AT-01..20 وC05-AT-01..20 وC06-AT-01..20 وC07-AT-01..22. هذه المعرفات لا تعني وجود نص حالة اختبار كاملة أو نتيجة تشغيل أو ربط دقيق بكل وظيفة. مصدر قوائمها هو أقسام B-01–B-07 وليس الفصل 163.
5. **نطاق الاستعادة:** الفصل 163 المتاح يتوقف عند C07 ويذكر أن C08–C14 متبقية في الجزء التالي. لا تستنتج معرفات أو تفاصيل C08–C14 من هذا الجزء.

## 4. إجراءات المطابقة المطلوبة

- إنشاء canonical screen registry يحفظ source_id وrepository_id وalias وsource locator وcenter owner وstatus.
- استعادة Function IDs الأصلية لـC01–C04 في سجل الوظائف، ثم مطابقتها مع الكتالوج التشغيلي 19.
- مطابقة C05–C07 بين 163 و12 و20، مع حفظ مصدر كل وصف وتصنيف المشتق.
- مطابقة كل معرف اختبار AT مع نصه الأصلي ومخرجاته وشروطه؛ إذا لم يستعد النص، يسجل SOURCE-ID-ONLY / TEST-DEFINITION-MISSING.
- تحديث 02 و12 و19 و20 فقط بعد إعداد crosswalk قابل للمراجعة؛ لا حذف ولا إعادة ترقيم.
- إضافة AX/REQ/DATA/API/PERM/EVIDENCE/RELEASE links لكل شاشة ووظيفة بعد اعتماد المالك.
- عدم اعتبار العدّ المتطابق أو وجود ID دليلاً على اكتمال وظيفة أو اختبارها.

## 5. بوابة الإغلاق

لا تعتبر تفاصيل C01–C07 مغلقة حتى:
1. اعتماد canonical ID لكل شاشة ووظيفة مع aliases للمراجع القديمة.
2. توثيق المصدر والمالك لكل وظيفة.
3. ربط الوظيفة بالمتطلبات والبيانات والصلاحيات والعقود.
4. وجود اختبار محدد قابل للتنفيذ وبيئة ونتيجة ودليل.
5. مراجعة التداخلات والاعتماديات مع بقية المراكز.
6. إغلاق الفجوات أو تسجيل استثناءات معتمدة.
