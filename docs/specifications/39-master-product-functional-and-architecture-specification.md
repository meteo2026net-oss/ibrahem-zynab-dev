## 1. الملخص التنفيذي

«مصمم التطبيقات الذكي» منصة تطوير تطبيقات متعددة المجالات والمنصات، تستخدم الذكاء الاصطناعي مع أدوات تصميم وتطوير مرئية، لتحويل فكرة المستخدم ومراجعه إلى مواصفات قابلة للمراجعة، ثم تصميم وبيانات ومنطق وكود واختبارات وحزم بناء ونشر وصيانة، مع بقاء القرارات ذات الأثر تحت إشراف المستخدم.

المنتج ليس مولد واجهات أو أكواد فقط؛ بل بيئة عمل متكاملة تشمل إدارة المشاريع، التصميم، الصفحات والتنقل، البيانات، البرمجة، وكلاء الذكاء الاصطناعي، الاختبار، الملفات، التكاملات، الأمن والحوكمة، البناء والنشر، المعرفة، الإعدادات، ولوحة التحكم.

**القاعدة الحاكمة:** الفكرة ← التحليل ← المواصفات ← التصميم ← الاعتماد ← التنفيذ ← التحقق ← البناء ← موافقة النشر ← التشغيل والصيانة.  
لا يبدأ توليد كود التطبيق أو تنفيذ تغييرات فعلية قبل اجتياز بوابات الاعتماد ذات الصلة. كما أن اعتماد مواصفات المنتج وموافقة بدء برمجته قراران منفصلان.

## 2. الرؤية والأهداف

### 2.1 أهداف المنتج
- تمكين المستخدم غير المبرمج والمطور من بناء تطبيقات احترافية عبر حوار طبيعي وأدوات مرئية.
- فهم مجال التطبيق والمستخدمين والأهداف والقيود قبل اقتراح التصميم.

- دعم التصميم الأساسي المشترك مع تخصيص ذكي مستقل لكل منصة.

## 6. الطبقات المعمارية العشر

1. **L1 — واجهة المستخدم:** shell والتنقل ولوحات العمل والتجاوب وRTL/LTR.
2. **L2 — تجربة التصميم:** محرر التصميم والمكونات ونظام التصميم والمعاينة.
3. **L3 — إدارة المشاريع:** دورة حياة المشروع والملفات والإصدارات وسياق العمل.
4. **L4 — محرك الذكاء الاصطناعي:** الوكلاء والمزودون والنماذج والتخطيط والاستدلال.
5. **L5 — محرك التنفيذ:** workflows وتوليد الكود والمهام المعزولة والتشغيل.
6. **L6 — البيانات والتكاملات:** التخزين والبيانات وواجهات API والموصلات.
7. **L7 — الجودة والتحقق:** الاختبارات والتحليل الساكن والتوافق والأدلة.
8. **L8 — الأمن والحوكمة:** الهوية والتفويض والسياسات والموافقات وسجل التدقيق.
9. **L9 — التشغيل والاستمرارية:** المراقبة والمهام الخلفية والتعافي والنسخ والاستعادة.
10. **L10 — البنية التحتية:** الحوسبة والشبكات والتخزين والبيئات والتوسع.

الفصل 132 يتضمن تجميعاً معمارياً تاريخياً مختلف الترقيم؛ تتم مواءمته مع L1–L10 عبر وثيقة crosswalk ولا يستبدل الطبقات الرسمية.

## 7. رحلة المستخدم وآلية العمل من البداية للنهاية

### المرحلة 1: بدء المشروع
- إنشاء مساحة عمل/مشروع وتحديد الاسم والوصف والمجال والمنصات المستهدفة.
- وصف الفكرة باللغة الطبيعية وإرفاق المراجع والملفات.
- تسجيل مالك المشروع والمؤسسة والأدوار وحدود الصلاحيات.

### المرحلة 2: الفهم والتحليل
- تحليل المجال والسياق والجمهور المستهدف وشخصيات المستخدمين.
- استخراج المتطلبات الوظيفية وغير الوظيفية والقيود والمخاطر.
- تحليل الصور والواجهات والمستندات والرسومات واستخراج عناصرها.
- كشف الغموض والتعارضات والافتراضات.
- طرح أسئلة تدريجية؛ سؤال واحد واضح في كل مرة عند الحاجة، مع عدم إعادة سؤال حُسم من قبل.
- حفظ الإجابات ومصادرها ودرجة الثقة والقرارات المفتوحة.

### المرحلة 3: تصور المنتج
- إعداد خريطة الوظائف والصفحات والأدوار وسيناريوهات الاستخدام.
- اقتراح تدفقات المستخدم والبدائل.
- عرض نطاق المشروع وما هو داخل النطاق وخارجه.
- عرض تقدير التعقيد والوقت والتكلفة والموارد كمؤشرات تقديرية موضحة الافتراضات.

### المرحلة 4: التصميم المرئي
- تصميم UI/UX قبل البرمجة.
- إنشاء التصميم بالذكاء الاصطناعي أو يدوياً أو بالجمع بينهما.
- محرر سحب وإفلات، خصائص، مكونات جاهزة ومخصصة ومولدة.
- تعديل مباشر من المعاينة مع سجل تغييرات وتراجع.
- نظام تصميم أساسي مع تخصيص مستقل لكل منصة.
- معاينات Android/iOS/Web/Desktop وأحجام هاتف/لوحي/كمبيوتر.
- اكتشاف تجاوز الحدود، النصوص المقطوعة، التداخل، اللمس غير الملائم والاختلافات غير المقصودة.
- لا يُعد الشكل المرئي وحده دليلاً على اكتمال وظيفة العنصر.

### المرحلة 5: الصفحات والتنقل
- مدير صفحات احترافي: مجلدات، بحث، ترتيب، نسخ، نقل، إعادة تسمية، إصدارات وحالات.
- خريطة تنقل بصرية تفاعلية للعقد والروابط والمسارات.
- كشف الصفحات اليتيمة والروابط المكسورة والمسارات غير المكتملة.
- إظهار اختلاف التنقل بحسب المنصة والدور.
- تحذير عند حذف صفحة أو تعديل مسار له ارتباطات، وطلب اعتماد التغيير المؤثر.

### المرحلة 6: وظائف العناصر وقواعد العمل
- محرر إجراءات مرئي ولغة طبيعية معاً.
- تحديد trigger، الشروط، الإجراءات، النتائج، معالجة الأخطاء والصلاحيات.
- عرض تسلسل المنطق الناتج عن AI للمراجعة قبل اعتماده.
- اختبار الحالات العادية والحدية والفشل والتزامن والصلاحيات.
- منع زر أو حقل أو عنصر واجهة بلا سلوك موثق من أن يُصنف مكتملاً.

### المرحلة 7: البيانات والتكاملات
- اقتراح نموذج البيانات والجداول والحقول والعلاقات ومصادر البيانات.
- مخطط مرئي قابل للتحرير يدوياً وباللغة الطبيعية.
- ربط الصفحات والعناصر بالبيانات والخدمات.
- تعريف ملكية كل كيان ومصدر الحقيقة وقواعد التحقق والاحتفاظ والحذف والتصدير.
- تحديد APIs والأحداث والعقود والإصدارات والأخطاء والمهل وإعادة المحاولة.
- عدم تغيير قواعد إنتاج أو خدمة خارجية أو مخطط حساس دون موافقة مطلوبة.

### المرحلة 8: المعمارية وخطة التنفيذ
- اقتراح التقنيات مع أسباب الاختيار والبدائل والتوافق والتكلفة.
- فصل تقنيات بناء المصمم عن التقنيات التي سيستخدمها التطبيق الناتج.
- وضع خطة تنفيذ ومهام واعتماديات ومخاطر ومراحل.
- توثيق القرار وحالته وصاحبه ومصدره وتاريخه وأثره.

### المرحلة 9: بوابة اعتماد المواصفات
- مراجعة المتطلبات والواجهات والتنقل والبيانات والتكاملات والصلاحيات والأمن والتكلفة.
- عرض الفجوات والتعارضات والافتراضات والقرارات المفتوحة.
- تصدير حزمة مواصفات للمراجعة.
- اعتماد المستخدم للمواصفات قرار مستقل؛ ولا يساوي الموافقة على بدء البرمجة.

### المرحلة 10: التنفيذ البرمجي
بعد الموافقة الصريحة على بدء التنفيذ:
- إنشاء هيكل المشروع والملفات والكود.
- حماية تعديلات المستخدم اليدوية وإظهار diff قبل الدمج.
- تنفيذ الوظائف والواجهات والبيانات والتكاملات.
- استخدام بيئات معزولة للعمليات غير الموثوقة.
- حفظ checkpoints وسجل التغييرات وإمكانية التراجع.
- عدم تنفيذ عملية حساسة إلا ضمن الصلاحيات والموافقات المحددة.

### المرحلة 11: الاختبارات وضمان الجودة
- اختبارات الوحدة والتكامل والقبول والواجهات والمنصات.
- اختبارات الأداء والأمن والخصوصية والعزل وإمكانية الوصول.
- اختبار قواعد البيانات وواجهات API والتكاملات.
- ربط كل نتيجة باختبار منفذ وإصدار وبيئة وسجل ونتيجة فعلية.
- لا يُعلن نجاح اختبار أو إصلاح أو نشر دون دليل تنفيذي.

### المرحلة 12: البناء والنشر
- بناء حزم المنصات وإدارة التوقيع والأسرار والإصدارات.
- مراجعة نتائج الاختبارات والأمن والاعتمادات.
- تقديم خطة النشر والتأثير والتراجع.

## 21. الأساس التقني وحالة الاعتماد

### 21.1 قرارات مثبتة في سياق الموافقات
- Angular هو الأساس المعتمد لواجهة مصمم التطبيقات نفسه، وليس Flutter Web.
- محرك التصميم ومحرك البرمجة مستقلان عن إطار واجهة المصمم.
- Monaco هو محرر الكود المرجعي في المواصفات الحالية، مع ضرورة مراجعة تفاصيل دمجه.
- دعم كل المنصات والتقنيات من خلال معمارية ومحولات لا عبر فرض تقنية واحدة على كل التطبيقات.
- المعمارية المعيارية والتوسع المستقبلي معتمدان من حيث المبدأ.
- إدارة الاعتماديات هجينة: الاختيار التلقائي للمهام العادية ضمن السياسات والميزانية، وموافقة المستخدم للقرارات المهمة أو عالية الأثر.

### 21.2 خيارات تقنية مبدئية وليست قرارات نهائية
NestJS/TypeScript، Python، PostgreSQL، تخزين S3-compatible، pgvector، Redis/Valkey، BullMQ، SSE/WebSocket، OpenTelemetry، GitHub Actions، OIDC/OAuth2، Keycloak وغيرها.  
تظل هذه خيارات مرجعية مقترحة تخضع للمقارنة والتوافق والتكلفة والأمان والقرار المعماري. لا تُعامل كاعتمادات نهائية دون سجل موافقة.

### 21.3 فصل تقنيات المصمم عن تقنيات التطبيقات الناتجة
يمكن للمصمم نفسه استخدام Angular، بينما يستطيع إنشاء تطبيقات باستخدام Flutter أو Kotlin أو React أو Vue أو Svelte أو تقنيات أخرى متى توفرت محولات واختبارات توافق. اختيار تقنية المصمم لا يقيد ناتج المستخدم.

تؤكد مصادر المتابعة الأحدث اعتماد المستخدم من حيث المبدأ:
1. الاستيراد الذكي للتطبيقات القائمة مع فصل التحليل عن التعديل وموافقة التعديل والنسخ الاحتياطي وdiff/rollback.
2. تعدد المستخدمين والمؤسسات وعزل البيانات والملفات والموارد.
3. المعمارية المعيارية والتوسع المستقبلي والتوافق مع الإصدارات.
4. حوكمة وكلاء AI والصلاحيات والمراقبة وسجل التدقيق المحمي والإيقاف.
5. استمرارية التشغيل والتعافي والنسخ الاحتياطي وRTO/RPO واختبارات الاستعادة.

وتشمل قرارات أخرى مثبتة في سجل المواصفات: التصميم قبل البرمجة، تصميم متعدد المنصات، مدير صفحات احترافي مع خريطة تنقل بصرية، الإنشاء بالذكاء الاصطناعي والإنشاء اليدوي معاً، محرر إجراءات مرئي ولغة طبيعية مع مراجعة واختبار، مركز معرفة مستقل لكل مشروع، إدارة اعتماديات هجينة، Angular لواجهة المصمم، وفصل محركات التصميم والبرمجة عنها.

**لا تُحوّل توصية أو مقترحاً إلى قرار معتمد بسبب تكراره في الوثائق.** يجب الرجوع إلى سجل القرارات ومصدر الموافقة. لا تُنشأ ADR جديدة قبل مطابقة ADR-001..028.
